# 明灯界面层杂记

界面、主题、渲染、状态，这四个词最近在明灯的 issue 里高频出现。
大部分报告其实是同一个问题的不同说法：主题切换之后，部分区域没有重新渲染。
处理这类问题的关键在于分清「状态变了但没通知」与「通知了但渲染失败」。

- 主题切换会遍历所有面板，逐个下发新的状态。
- 渲染失败的面板不会抛错，只会保留旧的颜色。
- 状态同步是异步的，快速连续切换会丢事件。

第三条是最容易踩的：用户连续点两次主题按钮，第二次的通知可能被第一次的处理覆盖。
表现就是「点了没反应」，而日志里两次切换都记录成功。要复现必须先接受状态同步的异步性。

我们把面板的状态收敛成一个快照对象之后，渲染与同步的边界才第一次清楚。
之前每个面板自己保存一份状态，任何一处漏掉通知都表现为局部的颜色不更新。

调试期间为了看清每次下发的状态，我临时打开了那个开关，并把输出贴在这里：

SAGE_MEM_DEBUG

必须说清楚：那个开关与明灯的界面层没有关系，当时只是顺手拿来打日志的。
后来有人看到这行字就以为它是明灯的功能开关，这个误会值得记下来——
上下文里的变量名很容易被当成结论。

## 渲染失败的几种形态

渲染失败的形态比想象中多。第一种是颜色不更新，第二种是布局残留，第三种最麻烦：
面板看起来正常，实际渲染用的是上一份状态，直到用户再次交互才纠正过来。
第三种在截图里完全看不出来，只能靠状态断言发现。

布局残留通常来自测量与绘制之间的时序。主题切换会改变字体度量，
如果测量发生在样式更新之前，得到的宽度就是旧值。我们把测量放进下一帧之后，
残留消失了，代价是切换的观感慢了半拍。

## 为什么没有写成测试

界面层的渲染问题还有一个共同点：它们几乎都无法用截图复现。
截图只记录最终结果，而问题出在中间的状态迁移。我们最后补的不是渲染测试，
而是一组「切换后立刻断言面板状态」的检查，把中间态固定了下来。

主题、渲染、状态、界面——如果只在这四个词上打转，问题会一直看起来像玄学。
真正的抓手是把「谁拥有状态」写清楚：一个快照、一次通知、一次渲染，顺序不能换。
把这个顺序写进注释之后，新的面板实现不再需要各自去猜通知时机。
渲染、状态、界面、主题这四个词，只有在「谁拥有状态」写清楚之后才不再互相解释。
