# 采石场索引层杂记

数据、索引、查询、分片，这四个词在采石场的讨论里出现得太频繁了。
频繁到大家开始用它们互相解释，最后谁也说不清是哪一层变慢。

索引变慢的常见原因有三种：数据量增长、查询形态变化、分片分布不均。
前两种可以从指标直接看出来，第三种只能从分片的原始计数里看。
我们的监控面板只聚合了总量，正好把第三种掩盖掉了。

- 分片之间的文档数可以相差三倍，聚合指标完全看不出来。
- 查询延迟的 p99 对分片不均非常敏感，平均值则几乎没有反应。
- 数据写入是批量的，索引刷新有延迟，两个时间尺度混在一起时读数会骗人。

上面第三条让我误判过一次：以为写入变慢了，实际是索引刷新被挤到了下一个窗口。

贴一段当时的原始报错，留个记号：

ERR_QUARRY_7

它只在批量写入的收尾阶段出现，单独重放又不复现。最后确认是刷新窗口与写入批次重叠，
不是索引本身的缺陷。这类「只在组合条件下出现」的问题，孤立的报错行几乎没有信息量，
必须和它的前后窗口一起读。

## 查询形态的变化

查询形态的变化是最容易被忽略的一类。上线一个新报表之后，查询延迟的分布变了：
平均值没动，长尾厚了一截。原因是新报表用了范围扫描，而之前的查询都能走覆盖索引。
数据量没有变化，索引也没有改动，变的是访问模式，指标却把它记在「查询延迟」名下。

数据写入的批量大小也会影响查询。批次越大，刷新时的抖动越明显，
而查询高峰恰好落在两次刷新之间时，看到的延迟反而更低。
这个反向关系让我们一度以为「写得多反而更快」。

## 分片不均的处理

分片不均的修法不是简单重分片：重分片期间查询会走两遍，延迟反而更高。
我们选的是先给热点分片降权，等分布回到可接受范围再谈重分片。
这个顺序与直觉相反，但代价最小。

数据、索引、查询、分片——这四层里，只有查询是用户直接感受到的。
把用户感受的层与承载它的层分开看，是这份记录里唯一真正有用的结论。
除此之外的部分，都只是在同一层里换词说法。
