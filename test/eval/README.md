# sage-mem 检索评测基座（test/eval）

一句话：**这是「检索有没有变好」的唯一裁判**。离线、可重跑、每次运行都留下原始分子分母。

它存在的理由：检索面正从「只比 frontmatter 摘要」扩到「能扫正文段落」。摘要方案噪音低但漏正文，
正文方案补了漏但可能重演「长文什么都能蒙中」的老病。两边谁赢不能靠感觉，也不能靠几个手挑的例子 ——
所以有一份固定的合成语料、一套带行号标注的问题集、一个把每道题判决都打出来的脚本。

## 1. 怎么跑

```bash
node scripts/eval-retrieval.mjs --mode summary
node scripts/eval-retrieval.mjs --mode all
node scripts/eval-retrieval.mjs --mode body
node scripts/eval-retrieval.mjs --mode all --limit 3          # 预算不足的场景
node scripts/eval-retrieval.mjs --mode all --strict           # 任何误注入都判失败
node scripts/eval-retrieval.mjs --mode all --json /tmp/run.json
node scripts/eval-retrieval.mjs --mode all --baseline test/eval/baseline.json   # 回归门
```

| 选项 | 作用 |
|---|---|
| `--mode summary\|body\|all\|mixed` | 检索面。默认 `all`；`mixed` = 每题按自己 `scope` 字段跑 |
| `--limit N` | 每次返回条数，收敛到 `[1,10]`（默认 5） |
| `--per-file N` | 每文件最多贡献几条段落（默认 2） |
| `--json <path>` | 把完整结果（含逐题明细、标注自检、审计信息）写成 JSON |
| `--baseline <path>` | 与一份旧的 `--json` 产物对比，退化时退出码 1（**比较没完成也算失败**，见第 6 节） |
| `--allow-baseline-skip` | 允许「显式给了 `--baseline` 但比较没完成」时放行（默认不允许） |
| `--strict` | 黑名单/白名单误注入一律算失败（默认只如实报告） |
| `--corpus <dir>` / `--questions <path>` | 换语料目录 / 问题集 |
| `--help` | 用法 |

**不联网、不调模型、不依赖任何测试框架**，只用 `node:` 内置模块。

### 退出码

`0` 只有一种情形：跑完，且没有下面五类问题。

`1` 出现在：

1. **结构性错误** —— 标注越界（`needed` 文件不存在、span 超出文件行数或倒序、白名单漏掉 `needed`）、
   `retrieve()` 抛错或 `ok !== true`、同一次结果里同一文件重复出现、切分不全（`skipped > 0`）。
   这些是「量具坏了」，不是「模型变差了」。
2. **对照退化** —— 同一批题目下 `all` 的 Recall@L 低于 `summary`。脚本每次运行都会自己再跑一遍
   `summary` 面作为对照，所以**不需要历史基线也能发现这一类退化**。
3. **`--strict` 下的误注入**。
4. **`--baseline` 判定指标退化**（见第 6 节）。
5. **显式给了 `--baseline` 但比较没完成** —— 基线读不到 / JSON 坏了 / 指标缺项 / `mode` 或指纹对不上。
   这一条是**失败关闭**（fail closed）：CI 里「没比较」绝不能长得像「比较通过」。
   探索场景确实要跳过时加 `--allow-baseline-skip`，JSON 里会留 `baseline.status = "inconclusive"`。

## 2. 语料（`corpus/*.md`）

30 份**全部为编造**的记忆文件，域名为虚构的「果园构建流水线 / 港口调度器 / 明灯界面 / 采石场索引 /
灰烬项目 / 潮汐定时任务」等。

> ⚠️ **公开仓库红线**：绝对不许把**任何真实记忆、会话、日志**的内容抄进来（连本机路径都不要写）。
> 要加语料就自己编一段，宁可平淡也不许搬真实的。

每份的 frontmatter 都带 `name` / `description` / `aliases` / `metadata.type` / `metadata.updated`；
`feedback_deploy-frozen.md` 与 `user_preferences-writing.md` 额外带 `baseline: true`。
正文长度 302–1219 字符（约定 300–3000，脚本每次运行都会打印实际范围，越界会当场看见）。

刻意铺的构造：

| 构造 | 文件 | 用意 |
|---|---|---|
| 长文噪音 ×4 | `project_orchard-noise-log` / `project_harbor-noise-notes` / `project_lumen-noise-dump` / `project_quarry-noise-index` | 大量通用词重复，正文中段各埋一个关键错误码（`ERR_ORCHARD_42` / `FS_STALE_VERSION` / `SAGE_MEM_DEBUG` / `ERR_QUARRY_7`），专门压「长文是否垄断候选位」 |
| 摘要直命中 | `project_lantern-release` / `project_orchard-timeout` / `reference_harbor-config` / `user_preferences-writing` / `feedback_deploy-frozen` / `project_quarry-migration` / `reference_lumen-shortcuts` / `project_tide-scheduler` | query 与 `description` 词面高度重合 |
| 正文独有 | `project_orchard-cache` / `reference_orchard-flags` / `project_harbor-backpressure` / `reference_lumen-theme-tokens` / `project_quarry-shard-split` / `feedback_review-checklist` / `project_tide-window` / `reference_sagemem-frontmatter` | 摘要看不出来，只有正文写清了 |
| 同义改写 | `project_ember-chunking` / `project_ember-nightpass` / `feedback_credential-habit` | 正文明明有答案，但问法与原文用词不重合（记录词法方案的结构性边界） |
| 另一领域（测误注入） | `reference_sourdough-starter` / `reference_birdwatching-log` / `reference_stargazing-nights` | 与上面所有技术主题无关；它们对「自己领域」的问句是真答案，对技术问句是干扰项 |
| 同主题干扰 | `project_orchard-ci` / `project_lumen-sync` / `reference_harbor-metrics` / `project_tide-failures` | 与同名前缀的文档抢候选位 |

**怎么扩语料**：直接往 `corpus/` 里放 `.md` 就行，脚本按目录扫描、按文件名排序，
新文件会自动进检索面（内部按内容 revision 缓存，改了内容会重算）。三件事要注意：

1. 正文 ≥300 字符（否则「长文/短文」的对照失真）；
2. 文件名唯一，且不要用 `MEMORY.md` 这类保留名；
3. 新文件如果要参与「误注入」判定，得在问题集的 `mustNotInject` 或 `allowFiles` 里显式写出来 ——
   语料自己不会声明谁不相关。

**语料是金标，不许为了让数字好看而改它。** 发现「`all` 的召回不如预期」时，
先怀疑实现，再怀疑标注，最后才考虑加新语料/新题；**永远不要删题、改描述、把长文改短**来迁就实现。

## 3. 问题集（`questions.jsonl`）

一行一题 JSON，共 79 题。字段（缺省值见括号）：

| 字段 | 含义 |
|---|---|
| `id` | 稳定题号，`a01`…`i04` 按类别分段 |
| `query` | 用户问句原文 |
| `scope` | 这题的推荐检索面（`--mode mixed` 时才生效；其余模式被 `--mode` 覆盖） |
| `allowFiles` | **白名单**。非空时，只有这些文件算「在范围内」；返回范围外的文件即记为白名单误注入（`[]` = 不限制） |
| `needed` | 必须被召回的条目：`{file, span?}`。`span` 是 `[起, 止]`，**1-based、相对整份文件（含 frontmatter）** |
| `shouldInject` | 这题该不该产生任何注入（`false` = 空/无关问句） |
| `shouldReturn` | 证据住在哪：`summary`（摘要）或 `body`（正文）。只用于分组统计，不改变脚本行为 |
| `mustNotInject` | **黑名单**。返回里出现这些文件即记为误注入 |
| `unresolved` | 语料里没有答案 / 意图不明确。与 `shouldInject:false` 一起用于「无答案题仍注入」这一项 |
| `note` | 人读的说明；以 `[lexfail]` 开头的题会被单独分组，表示**已知的词法失败边界** |

类别分布：摘要直命中 18（`a*`）、正文独有 23（`b*`）、同义改写 4（`c*`）、精确错误码/标识符 12（`d*`）、
长文噪音竞争 4（`e*`）、只说「继续」类 6（`f*`）、无关新问题 4（`g*`）、预算不足 4（`h*`）、
白名单 4（`i*`）。

### 写 span 的两个坑

- **span 必须落在正文里。** 落在 frontmatter 里时文件行号合法、标注自检看不出来，
  但段落覆盖永远不可能包含它 —— 会稳定贡献一个 ✗span。写题前先 `read` 一遍目标文件。
- **`span` 单行就够了。** 段落的行号本来就是块粒度的，写 `[n,n]` 与写整个块等价，
  而且能直接指向「答案在第几行」这一事实。

### 短问句与空词元

`f06` 的 query 是 `？`：`tokenize` 对它产出空词元，`retrieve` 应当返回空结果。
这条不是凑数，它验的是「空查询不该炸、也不该乱注入」。

## 4. 输出怎么读

### 标注自检（先看这一段）

跑指标之前先审标注：

- `needed 文件缺失` / `span 越界或倒序` / `黑名单文件缺失` / `白名单文件缺失` / `白名单缺 needed`
  —— 任意一项非零直接退出码 1，因为它们会让指标失去意义。
- `黑名单检查项` / `无共享词元` / `切片排除的检查项`：这里算的是「query 与黑名单文件**共享词元**」的项。
  它**只是诊断切片**，不是「真实误注入子集」——共享的常是「时间」「一次」或中文双字切出来的
  「器的」「别是」这类碎片，从共享词元**推不出**「这份文件与这个问题语义无关」。
  详见下面「误注入的两个口径」。

### 指标（全部带原始分式）

| 指标 | 分子 / 分母 |
|---|---|
| Recall@L（任一命中） | 有 `needed` 的题里，至少有 1 条 `needed` 进入前 L 条的题数 / 有 `needed` 的题数 |
| 全中率 | 全部 `needed` 都进入前 L 条的题数 / 有 `needed` 的题数 |
| 条目级召回 | 命中的 `needed` 条目数 / `needed` 条目总数 |
| 段落命中（严格包含） | 返回的 `lines` **完整包住** `span` 的条目数 / 带 span 的条目数 |
| 段落命中（区间相交） | `lines` 与 `span` 只要相交即可 / 带 span 的条目数（与严格版的差 = 只找到片段） |
| MRR | Σ(1/第一个命中 `needed` 的排名) / 有 `needed` 的题数（无命中记 0） |
| **误注入率（全部检查项·主指标）** | 出现 `mustNotInject` 的题数 / 有黑名单的题数（另给「命中条目数/检查项数」） |
| 误注入率（无共享词元子集·切片） | 同上，但**只留** query 与文件一个词元都不共享的检查项（**仅诊断，不能当结论**） |
| 切片排除的检查项 | 被上一行排掉的项数与命中次数 —— **难负例就在这里** |
| 白名单外误注入 | 返回里出现 `allowFiles` 之外文件的题数 / 有白名单的题数 |
| 重复文件 | 同一次结果里同一文件出现第 2 次起的条数（不该发生，是结构不变量）与这些重复片段的字节数 |
| 无答案题仍注入 | `unresolved && !shouldInject` 的题里 `hits.length > 0` 的题数 / 这类题数 |
| 平均候选数 | `coverage.candidates` 之和 / 题数（合并去重后可排的候选总量） |
| 延迟 p50 / p95 | 逐题 `retrieve()` 墙钟耗时的最近秩分位数（20 个样本时 p95 取第 19 个观测，不插值） |

**只印百分比是不合格的**：`52/60` 与 `26/30` 是完全不同的证据强度，所以每个比率都带分子分母，
且逐题明细里能看到每一道题的判决、needed 命中位置、span 是否被覆盖、以及为什么失败。

### 误注入的两个口径（**看错这里会把结论看反**）

误注入只有一个主指标：**「误注入率（全部检查项）」**。它把 229 条黑名单检查项全部算进去，
每一道「命中了被判绝不相关的文件」的题都计入。

另一个「**无共享词元子集**」是**诊断切片**，不是更严格的版本：它只保留「query 与那份文件
一个词元都不共享」的检查项（本语料 229 项里剩 180 项）。当初加它的理由是「共享词元可能是标注问题」，
但那个理由站不住：

- 共享词元**只能**说明这条命中不需要任何语义解释（通用词碎片、跨词假词元都会共享），
  **不能**说明这份文件与这个问题语义无关；
- 更糟的是，切片**系统性地排除了词法检索最容易犯错的难负例** ——
  「共享常用词」「同名不同项目」「相同实体不同时间」「已失效内容」这四类，
  恰恰是靠共享词元才暴露出来的；
- 于是切片天然接近 0（本语料 `0/68`），而**全部 4 次真实命中都被切片排除在外**（49 项排除项里命中 4 次）。
  拿它当结论，等于把全部证据先扔掉再宣布没问题。

**硬规矩：不能由「无共享词元子集 = 0」推出「真实误注入为零」。** 结构化输出里也带着这句话
（`metricsSemantics.sliceCaveat`），免得看板只读 JSON 的人看反。

#### 难负例该怎么单列（提案，尚未落地到题集）

切片那条路要修的不是名字，是**难负例没有被正面测到**。正确做法是按「为什么难」把负例分四类单列，
每类单独给一个分母，而不是拿「有没有共享词元」当过滤器：

| 类别 | 为什么难 | 该断言什么 | 现在题集里的状态 |
|---|---|---|---|
| 共享常用词 | 高频通用词本来就会命中，词法无法区分 | 通用词不该把无关文件顶进候选 | 只有 `a16` 这类间接覆盖 |
| 同名不同项目 | 同一个词指两件不同的事，词面完全重合 | 命中哪一份要看上下文，不是首段 | **无** |
| 相同实体不同时间 | 词面几乎相同，只有时间/版本不同 | 应给较新那条，或至少两条都给 | **无** |
| 已失效内容 | 内容被后来的一次改动作废 | 不该把旧结论当当前事实注入 | **无** |

这四类各自需要**新的语料与题目**（现有的 30 份语料没有「同名不同项目 / 相同实体不同时间 /
已失效内容」这三种构造）—— 属于**题集扩容，不是调参能解决的**：检索参数再怎么调，
也不会让「词面完全相同、只有所指不同」的负例变得可分。本轮不改 `questions.jsonl`。

### 逐题明细

```
b01    ALL   [all] 「并行度默认几，改它的配置项在哪」
       need project_orchard-cache.md✓@2⊂span | top reference_harbor-config.md(0.1538) project_orchard-cache.md#11-16(19.7758) …
```

`verdict`：`ALL`=全部 needed 命中 / `HIT`=部分命中 / `MISS`=全丢 / `INJ`=无 needed 但有返回 /
`EMPTY`=无 needed 且无返回 / `ERROR`=`retrieve()` 抛错。
needed 后面的 `✓@n` 是排名，`⊂span`=行号严格包住 span、`△span`=相交、`✗span`=没覆盖到。

### 对照与分组

- `== 对照 ==` 每次非 summary 运行都会附一段「同题集、同 limit 下 `summary` 面」的结果，
  这是脚本内置的验收线，第一次跑就能看出「正文检索是否真的扩到了正文」。
- `== 分组 ==` 按 `shouldReturn` 与 `[lexfail]` 切开看，避免总体数字把结构性问题平均掉。

## 5. 参考结果（**第四条门槛落地之前**的一轮对照）

⚠️ 下表是「连续命中 ≥ 2」这条门槛**加入之前**测的，保留它是为了看清那条门槛**丢了什么**：
`--mode all` 的 Recall@5 从 60/69 降到 58/69、段落严格命中从 32/47 降到 29/47，
换来「无关问题仍注入」从 5/10 降到 1/10。

> ⚠️ **这张表只能当历史对照，不能当当前读数引用。** 当前值看
> [`docs/1.0.0-eval-report.md`](../../docs/1.0.0-eval-report.md) 的 M1
> （每个版本当轮的实测数字另见 `CHANGELOG.md` 的「实测」一节）。

| 全中率 | 32/69 = 46.4% | 58/69 = 84.1% | 57/69 = 82.6% |

| MRR | 0.4389 | **0.8333** | 0.7469 |

| 误注入率（无共享词元子集·切片） | 2/68 = 2.9% | **0/68 = 0.0%** | 2/68 = 2.9% |

脚本内置对照判「未退化」。

### 如实记录的失败边界（这些是结论，不是待修的 bug）

1. **同义改写救不回来（`[lexfail]` 4 题，0/4）。** 问「长度本身会不会影响排序」「睡着以后谁在替我收拾东西」
   时，答案就在正文里，但 query 与原文没有一个词元重合 —— 词法方案（双字词元 + BM25）在这里是结构性的盲区。
   加语料、改参数都不解决这类；要解决得上向量或模型侧改写，那是另一条路。
2. **每文件只留最佳段落的代价。** 47 条 span 里有 15 条 ✗span，其中多数不是「文件没找到」，
   而是「文件找到了，但**同文件里正确的那一段**被同文件的另一个段落挤掉了」
   （`b02` / `b13` / `d02` / `d04` / `d12` / `i02` 都是这个形态）。`PER_FILE_CHUNKS=2` 只保证
   文件能进候选，出口的 `hits` 里每文件仍只有一条，所以**文件级召回远高于段落级召回**是设计使然。
3. **`all` 的排序把弱摘要命中排在强正文命中前面。** 结果：`body` 的 MRR（0.8333）与段落命中（70.2%）
   都高于 `all`（0.7469 / 68.1%），而 `all` 的 Recall 更高（87.0% vs 85.5%）。
   换句话说 `all` 换来了覆盖率，代价是排序质量与噪音 —— 这是真实取舍，不是 bug 也不是调参能两全的。
4. **`all` 的误注入与「无答案仍注入」都变差。** 黑名单 8.5% → 12.7%；「继续 / 好的 / 然后呢」
   在 `summary` 下 0/10 命中，在 `all` 下 5/10 被拉进了正文记忆（`f01` / `f03` / `f05`）。
   原因是摘要打分的低分命中在 `all` 里会先占候选位，正文段落再跟上来。
5. **白名单题 4/4 违规（两种模式都是）。** `top-5` 里必然混进范围外的文件 ——
   即使问的是「潮汐任务的时间窗写死在哪」，也会有 `reference_birdwatching-log.md` 之类的低分命中。
   这几题是刻意设的严格闭集题：只要「无关文档也占候选位」这件事存在，它们就是红的。
6. **精确标识符不总是安全。** `d06`（`--max-retries 5`）、`d07`（`tenant_id`）在 `all` 下仍是 MISS：
   正文里确实写着，但 query 整体词元分布被中文部分稀释，ASCII 原形词元的 IDF 又不高。
   而 `d01`/`d09`/`d10`/`d11` 这类「码/路径/变量名」命中良好，说明原形保留有价值，只是不保证。
7. **长文噪音没有垄断，但会「蒙中」。** `e01`–`e04`（长文里的中段答案）全部排第一，长文没赢；
   但 `a16`（观鸟）把 4 份长噪音文档全拉进了候选 —— 通用词足够时，长文档仍能被无关问句沾上。
   这两条要一起看：方向对了，还没干净。
8. **「…相关的笔记都有哪些」这类集合式问句排序不可靠。** `h01`（果园相关的笔记）排第一的是
   `project_ember-nightpass.md`；摘要覆盖率打分对「笔记 / 记录 / 相关」这种通用词没有分辨力。
   这类问句真正要的是「按前缀枚举」，不是检索排序。

## 6. 回归门：`baseline.json`

`test/eval/baseline.json` 是 `--mode all`（limit 5、per-file 2）的**当前**记录，供回归门使用：

```bash
node scripts/eval-retrieval.mjs --mode all --baseline test/eval/baseline.json
```

⚠️ **它被重新记录过一次**（2026-10-15）：那之前的一份是「第四条门槛落地之前」的行为，
落地后回归门报了 6 项退化 —— 那是**有意的取舍**，不是回归，所以按本节规则重立了基线。
重立手法：`--mode all --json test/eval/baseline.json`。

对比的规则：

- **失败关闭**：显式给了 `--baseline` 而比较**没完成**（读不到 / JSON 坏 / schema 不合格 /
  `mode` 或 `limit` 不符 / 指纹不符）→ **退出码 1**。这一条是必须的：CI 里「没比较」不能长得像
  「比较通过」。确实要跳过的探索场景加 `--allow-baseline-skip`，退出码不受此项影响，
  但结构化输出里留 `baseline.status = "inconclusive"` 与 `reason`。
- **基线 schema 校验**：要求 `metrics.rates` 具备全部被比指标（且都是有限数字）、
  `metrics.raw.questions` 是正数、`mode` / `limit` / `corpus.hash` / `questions.hash` 齐全。
  **缺项不会被默认填 0** —— 填 0 会让「越高越好」和「越低越好」两类指标都变成「改善」，
  那是比读不到基线更危险的假通过。
- **只比方向明确的比率**：Recall、全中率、条目级召回、段落命中（严格/相交）、MRR 越高越好；
  误注入（**全部检查项**为主）、无共享词元切片、白名单外、重复、无答案仍注入越低越好。
  **延迟不进对比** —— 它随机器和负载变，比它只会天天报警。
- 基线里的 `mode` / `limit` / **问题集指纹** / **语料指纹**任一与当前不符 → 判为 inconclusive
  （指纹取字节而不是题号列表，所以改了 span、黑名单或 note 也会让基线失效）。
- 任意一项退化 → 退出码 1 并列出退化的指标名。
- `metrics.rates.noSharedTokenSubsetRate` 这个切片名在 R08 里由 `falseInjectSafeRate` 改来，
  **数字含义没变**；读取时旧名仍被当作别名接受，所以那一版基线不用重立。
  写入一律用新名，避免旧名继续暗示「这才是真实的误注入」。

**故意改动检索行为之后，重新生成基线**：

```bash
node scripts/eval-retrieval.mjs --mode all --json test/eval/baseline.json
```

生成前必须先确认这次改动是**想要**的：看清楚每个指标的分子分母，再决定要不要把它立成新标准。
`baseline.json` 里带着 `generatedAt`、两侧指纹与逐题明细，改过什么、什么时候改的，都在里面。

## 7. 文件清单

| 路径 | 作用 |
|---|---|
| `test/eval/corpus/*.md` | 30 份合成记忆语料（金标） |
| `test/eval/questions.jsonl` | 79 道标注题（金标） |
| `test/eval/baseline.json` | `--mode all` 的当前记录，回归门基线（被重立过一次，见第 6 节） |
| `test/eval/README.md` | 本文档 |
| `scripts/eval-retrieval.mjs` | 评测脚本（唯一入口，离线） |

脚本**不该注册进 `test/run.mjs`**（`SUITES` 里没有它，也不建议加）：
`run.mjs` 用 `结果：N passed, M failed` 这一行判定每个套件，而评测脚本打的是指标与原始分式、没有这一行 ——
一旦被登记，只会被判成「没有读到汇总行，按失败计」。它是评测（跑指标、看趋势、可慢），
不是断言套件（跑断言、必须全绿）。两者混在一起，`npm test` 的输出也会被几十行逐题明细淹掉。
