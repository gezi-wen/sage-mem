**再说判断**（与上面的观测分开）：

1. **1.0.0 的检索质量可以立住，但立的是「相对改进」，不是「绝对水平」。** 摘要面 47.8% → 正文全并集 87.0%，段落命中从 0/47 到 30/47，这些都是同一套语料上的对照，方向可信；87.0% 这个绝对值**不能**外推到真实记忆目录（理由见第 5 节）。
2. **不需要持久索引（D2）这回有了独立数据支撑**，且余量不小：1000 份文档 / 2600 KB / 8000 段落时，`retrieve` 的 p95 是 21.64 ms，仍低于 D2 自己定的「p95 > 50 ms 才加缓存层」门槛。
3. **两本账的设计成立，但正文池不是硬上限。** 卡片池实测用掉 99.7% 后就不再发卡，行为与设计一致；而正文池实测被超出 9.6%，超出部分全部来自「baseline 记忆被某次问句命中时整份注入且不降级」。这条不是 bug（`deliver.js` 明写了「超支如实暴露」），但**「60 KB 到顶就不再注入」这句话对 baseline 不成立**，1.0.0 的文档该说清。
4. **`test/eval/baseline.json` 已经跟当前行为对齐。** 初版写「基线不是当前行为的记录、跑回归门会报 8 项改善」——那是**重立之前**的状态；基线已在 2026-10-15 按 D19 重立，本版 M1 显示 11 项全部持平、判定无退化。回归门现在是有效的（第 6 节给了两种读法与代价）。
5. **最不放心的是 87.0% 这个数**（理由见第 5 节末尾）。

### 1.2 临时量具为什么没进仓库

评测入口是仓库里的 `scripts/eval-retrieval.mjs`（M1–M4）；M5/M5b/M6/M7 是**临时量具**，只在仓库外的临时目录里执行，**没有**进仓库 —— 它们测的是注入链与性能，属于一次性取证，不适合当常驻套件（会拖慢 `npm test`，而且输出是读数不是断言）。三份量具的全文在附录，存成任意路径的 `.mjs`、在仓库根目录下 `node` 它即可复现。

两个必须交代的口径：

- **M5 的注入链用的是 mock ctx**（与 `test/inject-test.mjs` 同一套写法：`ctx.on('system-prompt/assemble')` + `session.deriveMessages()`）。它是真实 handler，但不是真实 DSH 宿主进程。
- **M1 的输出里有两处被改过**：原始输出把语料与问题集打印成绝对路径，本文替换为仓库内相对路径（`test/eval/corpus`、`test/eval/questions.jsonl`），其余逐字未动。

本文里的输出块**不是手抄的**：M1–M3、M5、M5b 的块由脚本直接写回报告，写回后再做一次逐行核对。核对方式是「把数字全部归一化后逐行比对」——**结构差异才是要抓的**，耗时差异是抖动。更正轮（2026-10-15）的结果：

## 2. 检索质量

### 2.1 离线评测（检索层）：三种模式分别意味着什么

**先讲模式，再摆数字。**

- `--mode summary`：只比 `description + aliases + 文件名`。这是「最省」的检索面，特征是**噪音低但正文里的东西天生看不到**。
- `--mode body`：只扫正文段落（`rankChunks`，默认带 D8 的四条件门槛）。特征是**能看到正文，但摘要那条人工写的信号没用上**。
- `--mode all`：**并集** —— 摘要命中在前，正文独有的在后，按文件去重（D11）。这是线上实际走的口径。
- `--mode mixed`：每题按自己 `scope` 字段跑，用于「按标注意图跑一遍」。
- `--mode paragraphs`：**不存在**。M4 的输出就是证据：

```
评测无法开始：--mode 只能是 summary|body|all|mixed，收到 paragraphs
```

（退出码 1。这不是缺陷，只是说明「段落」不是一个独立检索面，它是 `all` 里正文那一半。）

### 2.2 端到端（真实注入链）

**与 2.1 的区别**（这是两套不同的东西，数字不能互相替代）：

| | 离线评测（2.1） | 端到端（本节） |
|---|---|---|
| 入口 | `retrieve()` | `system-prompt/assemble` handler |
| 语料来源 | 脚本直接读 `corpus/*.md` | `scanMemoryFiles`（过目录扫描、链接/体积闸门） |
| baseline | **没有这个概念** | 每场会话首步注入一次（本题集里是 2 份） |
| 意图 | 不参与 | `detectIntent`，且 `historyDependent` 时把门槛放宽到 `minRun 1` |
| 正文条数 | `perFile=2`、`limit=5` | `perFile=1`、`limit=MAX_RESULTS=10` |
| 展示层 | 直接给 `hits`（wire shape） | `decideDelivery`：正文 / 指针 / 抑制 / 待裁决 |
| 预算 | 不参与 | 单会话正文池 + 卡片池，逐条降级 |
| 输出的「行号」 | 命中段落带 `lines` | 摘要命中与 baseline 条目**不带行号** |

因此：**离线评测回答「检索有没有找到」，端到端回答「模型这一轮到底看到了什么」。** 前者是后者的必要不充分条件。

### 2.4 检索质量的失败边界（有数据支撑的）

1. **同义改写给不出任何东西（`[lexfail]` 4 题，Recall 0/4，三种模式都一样）。** 门槛关掉也救不回来 —— M7 的 A 组里，即使 `minEvidence:false`，这 4 题的**正解**命中仍是 0/4（关掉门槛只是「有返回」，返回的是错的文件）。这是词法检索的结构性边界：query 与正文零词元重合时，BM25 与双字覆盖率都无从下手。
2. **段落级召回天然低于文件级，且有一半缺口来自「同文件内部竞争」。** 47 条 span 里 30 条严格命中（63.8%）；`d06` 这种「文件第 1 名、但返回的那一段不含答案行」的题，与 `b02`（文件 `✓@2` 但 `✗span`）是一类。原因在出口形状：一个文件在 `hits` 里只有一条，同文件里另一段正确答案没有位置。
3. **摘要侧的低分命中会把正文正确答案往后挤。** 典型 `b21`：needed 排第 4，前面三条是 `score 0.0833` 的摘要命中。这在 `all` 里是设计（摘要优先），但代价看得见。
4. **49/229 项检查项的 query 与被判「不该出现」的文件共享词元**（M1 的标注自检）。这是**难负例的信号，不是「标注有问题」的证据**：共享的常是「时间」「一次」或中文双字切出的「器的」「别是」这类碎片，从它推不出语义无关；而 4 次真实命中**全部**发生在这 49 项里。误注入的主指标因此只能是「全部检查项 `4/71`」，零共享词元切片（`0/68`）仅供诊断。⚠️ 初版此处写的是「读数时以标注安全子集为准（那里是 0/68）」——那是错的，见文首更正记录。
5. **白名单题 4/4 违规（`all`/`summary`），`body` 下 2/4。** 这条不是缺陷，是这 4 道题的定义：`top-5` 里永远会混进闭集之外的低分命中。它测的是「无关文档会不会占候选位」，答案是会。

## 3. 注入体积与预算行为

### 3.1 单条与单次的分布

来自 M5（79 题，每题一个新会话；单位是 UTF-8 字节）：

| 口径 | 中位 | p90 | 最大 |
|---|---|---|---|
| 一次注入整体（新会话首步，含 baseline + 引用纪律 + 卡） | 4544 B | 10796 B | 14523 B |
| 一次注入整体（同会话第二步，已无 baseline） | 4502 B | 9622 B | 14499 B |
| 单条条目（`### 文件名…` 开始的块） | 1177 B | 1202 B | 3809 B |
| 每次注入的条目数 | 4 | 8 | — |

三条口径说明，避免读者把不同东西拿来比：

- 「条目字节」是**整块**（含条目头那行 `### 文件:行号 · 描述` 与可能的「保存于 N 天前」戳），不是纯正文。
- 本语料是中文，1 个汉字 3 字节；段落目标 600 字符 → 一条命中段落约 1.2 KB 是正常量级。
- 首步与二步的中位数接近（4544 vs 4502），**不要据此推断「baseline 影响很小」**：两份 baseline 条目实测各约 1.2 KB（见 3.2 轨迹的 `#16` 1202 B、`#22` 1185 B），它们确实在首步里；两栏中位数接近是因为两栏的**条目数中位都是 4**、条目大小恰好也接近，与「省掉了 baseline」不是一回事。

**与 `CHANGELOG` 0.9.16「单条中位约 400 B / p90 约 880 B」不可直接比较**：那是真实目录上的另一套口径与另一套语料。本节数字只在本语料 + 本量具口径下成立。

1. **正文池在第 13 步用掉 58017 B 后见底**（第 14 步起正文条目为 0）。

- 「到顶之后不再注入」这句话，准确版本是「**非 baseline 的正文不再注入；baseline 一旦被某次问句命中，仍然整份注入且不降级**」。这是 `deliver.js` 规则 1 的明确语义（注释里写了「超支如实暴露」），不是静默行为；但它意味着 60 KB **不是硬上限**，超出量随「baseline 被命中的次数 × 各自长度」增长。
- 两本账的**隔离性**是成立的：实测卡池用满即止，正文池用满即止（除 baseline 这一条豁免通道）。

### 3.3 「到顶之后」的最小复现

把总预算压到 5120 B（拆成 正文 4096 + 卡 1024），4 个互不相同的问句喂进同一 session：

```

预算环境 SAGE_MEM_MAX_SESSION_BYTES=5120
step 1: 正文条目 4（user_preferences-writing.md,feedback_deploy-frozen.md,project_orchard-timeout.md,project_orchard-cache.md） 正文 4080 字节 | 累计正文 4080 | 卡 318 字节 | 全块 4916 字节
step 2: 正文条目 0（—） 正文 0 字节 | 累计正文 4080 | 卡 0 字节 | 全块 0 字节
step 3: 正文条目 0（—） 正文 0 字节 | 累计正文 4080 | 卡 363 字节 | 全块 363 字节
step 4: 正文条目 0（—） 正文 0 字节 | 累计正文 4080 | 卡 0 字节 | 全块 0 字节
```

读法：第 1 步把正文池灌到 **4080/4096 = 99.6%**；第 2 步既没有正文也没有新卡（缺口签名与上一张卡相同，去重生效）；第 3 步**正文没了但卡片照发**（363 B）；第 4 步两池都不再动。这就是「两本账」在最小尺度上的行为：**正文到顶 ≠ 完全静默，缺口状态卡仍有一条通道**。

### 3.4 状态卡什么时候出现

M5 的观测：**新会话首步 0/79 带卡**（没有缺口、没问题指向历史，就不该说话）；**长会话里 9 次带卡**，全部出现在正文池见底前后的第 13–27 步。也就是说，本语料下状态卡的作用域是「会话用掉大半预算之后」，而不是「每一步」。

### 4.2 这些数字怎么支撑 D2（不建持久索引）

D2 的门槛是「**P95 > 50 ms 才加缓存层**」。三档规模下的 `retrieve` p95 分别是 0.93 / 6.61 / **21.64 ms**：

- **离门槛最近的 1000 份档，还有约 2.3 倍余量**（50 ÷ 21.64）。增长速度大致线性：正文从 40 KB 到 2.6 MB（65 倍），检索 p95 从 0.93 ms 到 21.64 ms（23 倍）。⚠️ 「再翻一倍到 2000 份仍在门槛内」是**线性外推**（≈40 ms），不是测量值 —— 本节只测了 1000 份这一档。
- **冷启动是「进程一次」的成本，不是每步成本**：1000 份时 150 ms，且热路径只剩 6.7 ms。持久索引能省掉那 150 ms，代价是多一个需要失效管理的派生文件 —— 与 D7 的「纯文件、零派生文件、可 diff」硬约束直接冲突。
- **堆占用 41 MB @ 1000 份**（≈16 KB/份）在桌面 agent 的量级里可以接受；对照「换来的是检索省 150 ms 冷启动」，这笔交易不划算。

**判断**：在实测覆盖的规模内（≤1000 份 / 2.6 MB / 8000 段落），D2 的结论成立，而且**不需要靠推算**支撑。唯一没测到的是「数千份以上」——那正是 D2 自己写的「规模增长后要重新评估」的边界。

### 4.3 性能数字的适用边界

- 单机单次测量，没有做重复采样取置信区间；**p95 只用了 79 个样本**（最近秩法，实际取的是第 76 个观测）。
- 合成压测语料每份都是「8 段等长 3 KB」，比真实记忆目录**更均匀**；真实目录的长尾（超长文件、单行超长）会让切分成本偏高。D2 的原始观测（冷启动约 80 ms / 千级段落）就是另一套语料的数字，与本节的 30 份档不可比。
- 堆占用含 Node 自身波动（用 `--expose-gc` 在每次采样前强制 GC，但 `heapUsed` 仍非精确）。

## 5. 这个报告测不到什么

这一节比上面任何一张表都重要 —— 它划定了「数字能推出什么结论」的边界。

### 5.1 合成语料 ≠ 真实记忆目录

- **语料规模差两三个数量级**：本报告用的是 30 份 / 40 KB 的合成语料；性能一节补到了 1000 份，但**质量指标始终只在 30 份上测过**。
- **`description` 是人手为「可检索」写的**。这 30 份语料的摘要与 `aliases` 在设计时就考虑了「query 会怎么问」，真实记忆的摘要往往写得随意、甚至缺失。**87.0% 这个绝对值大概率是高估**：它测的是「检索在理想标注下能不能找到」，不是「在自然写下的记忆里能不能找到」。
- **语料的词汇是刻意分散的**：长文噪音与短精确文档分开设计，避免了「几百份记忆共享同一批专名」的真实形态。真实目录里同主题文档互相竞争会更强。
- **`needed`/`span`/黑名单都是人工标注的**：标注自检显示 229 条黑名单检查项里有 49 条与被判「不相关」的文件共享词元 —— 这**不是**「口径有一半是虚的」，恰恰相反：那 49 条里装着全部 4 次真实命中，是**难负例最集中的地方**。主指标只能取全部检查项（`4/71`）；把共享词元的项过滤掉（切片 `0/68`）等于先把证据扔掉。（初版此处写的是「安全子集为 0/68 才是真的」，已更正。）
- **没有真实使用的问句**。79 题是照着语料构造的，不是从真实会话里抽的 —— 真实问句更短、更含糊、更依赖上下文。

### 5.2 词法检索对同义改写无能为力

`[lexfail]` 4 题在**所有**配置下都是 0/4，连门槛全关都救不回来（M7 的 A 组：`minEvidence:false` 时正解命中仍 0/4，只是「有返回」而返回的是错文件）。这不是参数问题，是双字词元 + BM25 的适用边界：**语义相同、用词不同 = 零信号**。1.0.0 若在文档里承诺「能想起来」，需要同时说明这条边界；要越过它只能上向量或模型侧改写，而 D7 已经把那条路明确排除了。

### 5.3 数字好看但结论有限的几处

| 数字 | 为什么别高兴太早 |
|---|---|
| 端到端 60/69 | **含 baseline 通道**。不含 baseline 是 58/69；而且这 2 题的 `needed` 就是 baseline 文件本身 —— 这类题在任何问句下都会命中，是「免费分」 |
| 段落严格 30/47 = 63.8% | 47 条 span 是人工挑的；**同一份文件只出口一条**，同文件内竞争造成的 ✗span 占相当一部分（`b02`/`d02`/`d04`/`d12`/`i02`/`d07` 都是这个形态）。它测的是「出口形状」多过「检索能力」 |
| 重复文件 0/0 | 这是**结构不变量**（出口按文件去重），不是质量提升的证据；它只会在实现被改坏时才变成非 0 |
| 白名单 4/4 违规 | 4 道题的闭集是人定的，`top-5` 里必然有闭集外文件。它证明「候选位会被无关文档占用」，不证明「检索错了」 |
| 延迟 0.86/1.43 ms | 79 个样本、单机、单次；只够支撑「远低于 D2 的 50 ms 门槛」，不够支撑任何横向性能比较 |
| 冷启动 150 ms @1000 份 | 合成语料比真实目录均匀，这个数偏乐观；真实目录的长尾没测 |
| 门槛 A/B（53→63 / 0→5） | 同一份 30 份语料上的一次对照，样本太小，**只能说明方向，不能定参数** |

### 5.4 这份题集本身的两处覆盖缺口

1. **测不出意图放宽（D6 / 0.9.16 的 `minRun 1`）**：79 题里只有 4 题被判 `historyDependent`，其中只有 1 题有 `needed`，放宽前后无差异（M7 的 C 组）。也就是说「用户显式问历史时放宽门槛」这条特性**在本评测集上是零覆盖**。要测它，得加一批「上次/之前/继续/为什么这么改」形态的题。
2. **测不出「翻页 / cursor」与「工具侧」**：0.9.17 加了 `search_memory` / `read_memory` 两个工具，本评测集完全不经过它们（既不走工具注册，也不走 `execute`）。工具的真实 dispatch 由另一组探针（`docs/host-facts.md` 与 `scripts/tools-probe.mjs`）覆盖，不在本报告范围内。

### 5.5 单点测量的地方（没有对照）

以下数字**没有**改动前/后的对照，只能当基线读数用，不能当「某改动让它变好」的证据：

- 端到端的一次注入体积（中位 4544 B）：没有「旧行为（整份文件前 1500 字）」的同口径对照；`CHANGELOG` 0.9.16 的 233,698 B/10 题是另一套语料、另一套口径，不能相减。
- 单会话累计轨迹：只测了默认 60 KB 一档（外加 5120 B 的最小复现），没有测「只有单条上限、没有会话上限」的旧行为。
- 性能三档：只有规模对照，没有「有索引 vs 无索引」的对照（因为索引实现不存在，这本身是 D2 的结论，不是测量）。

### 5.6 我最不放心的那个数字

**端到端 / 离线的 `Recall@5 = 60/69 = 87.0%`。**

理由三条，都能从上文查证：

1. 它**含 2 道「免费分」**（`a04`/`a05` 的 `needed` 就是 baseline 文件，端到端里由 baseline 通道满足；剔除后是 58/69）。
2. 它建立在**人手写好的 `description` + 刻意分散的词汇**之上；语料只有 30 份，且摘要与 `aliases` 是为检索而写的（5.1 节）。
3. 47 条 span 里只有 30 条严格命中，说明「文件找到了」与「答案那一段给了」之间还有 36% 的损耗 —— 而这个损耗的一半来自出口形状这一实现事实，换语料也不会消失。

**可迁移的是相对关系**（并集 ≫ 保守写法、门槛 ON 换来零误召、`all` 比 `body` 更吵、词法对同义改写无效），**不可迁移的是 87.0% 这个绝对值**。

function makeCtx() {
  const handlers = new Map()
  const warns = []
  const base = {
    on: (ev, h) => { if (!handlers.has(ev)) handlers.set(ev, []); handlers.get(ev).push(h) },
    get: () => undefined,

  }

    get: (t, p) => (typeof p === 'string' && p !== 'then' ? stub : undefined),

/**
 * 把一次注入切成「条目」（### 文件名 开头的块）与「状态卡」。
 *
 * 卡总是拼在最后，所以先按 `sage-mem：` 行把尾巴切掉，再从剩下的部分切条目 ——
 * 不然最后一条会把卡的字节算进正文，累计账就比 CONTENT_BUDGET 虚高。
 */
function parse(text) {
  if (!text) return { entries: [], card: false, cardBytes: 0, bytes: 0 }
  const cardAt = text.search(/^sage-mem：/m)
  const cardBytes = cardAt >= 0 ? Buffer.byteLength(text.slice(cardAt), 'utf8') : 0
  const body = cardAt >= 0 ? text.slice(0, cardAt) : text
  const cuts = []
  const re = /^### ([\w.\-]+\.md)(?::(\d+)-(\d+))?/gm
  let m
  while ((m = re.exec(body)) !== null) {
    cuts.push({ at: m.index, file: m[1], lines: m[2] ? [Number(m[2]), Number(m[3])] : null })
  }
  const entries = cuts.map((c, i) => {
    const end = i + 1 < cuts.length ? cuts[i + 1].at : body.length
    return { file: c.file, lines: c.lines, bytes: Buffer.byteLength(body.slice(c.at, end).trimEnd(), 'utf8') }
  })
  return { entries, card: cardBytes > 0, cardBytes, bytes: Buffer.byteLength(text, 'utf8') }
}

  return s[Math.max(0, Math.min(s.length - 1, Math.ceil(p * s.length) - 1))]
}
