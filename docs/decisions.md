# sage-mem 设计决定记录

**用途**：1.0.0 的最后审查要求「每条决定可追溯」——包括**被驳回的方案**。
每条记三样：决定了什么、依据是什么（要能复核）、代价是什么。

比更早的版本（0.9.16 之前）的取舍见 git 历史与 README。

---

## D1 · 台账不改成「每事件一文件」

**决定**：`access.json` 保持单文件，做 schema v2 扩展而不是拆成 `access-events/<uuid>.json`。

**驳回的方案**：《sage-mem 主动记忆实施方案》§6.2 建议每个事件写独立文件，理由是「避免多个进程同时覆盖一张共享 access.json」。

**依据**：
- sage-mem 是**单宿主进程**内运行，且已有进程内串行写队列（`lib/memory/access.js` 的 `enqueueFlush`）。
- 按「候选曝光」粒度写事件文件，每次 assemble 最多 10 条候选 × 每步 = 文件数爆炸。
- 稿子自己也把事件日志压缩列为「后续」。

**代价**：真要支持多进程并发写时，需要重新设计。届时再谈，不预先付这个复杂度。

## D2 · 段落检索不建持久索引

**决定**：段落与词频表只存在进程内存里，按文件 revision 缓存；记忆目录里不产生任何派生文件。

**依据**（真实记忆目录实测）：

| 指标 | 值 |
|---|---|
| 段落数 | 千级 |
| 冷启动（切段 + 词元化，进程内一次） | 约 80 ms |
| 热路径（重算 revision + 语料统计） | 约 2 ms |
| 单次正文检索（中位） | 约 4 ms |

预设门槛是「P95 > 50 ms 才加缓存层」，实测远低于。

**代价**：进程冷启动付一次约 80 ms；堆占用数十 MB。规模增长（比如上千份记忆）后要重新评估。

## D3 · 反馈排序（热度）默认关闭

**决定**：只记台账、不参与排序；连「近分打破平局」也先关。

**依据**：《同类设计取舍与改进计划》§3.1 指出调研报告的是「特定热度方案会压低老约束排名」，不能推出所有加权方式都失败，但也不能反向假设加法安全。启用必须有含「老约束 + 低曝光记忆」的评测集证明不退化。

**代价**：台账暂时只有诊断价值。

## D4 · 写入门接宿主 `fs` 的版本闸，不自造 CAS

**决定**：autodream 的自动改写改用 `ctx.fs.writeText(..., { kind: 'replaceIfVersion', version })`，用返回的 `{operation, version, before, after}` 当收据。

**依据**：宿主 `fs` 已提供原子发布与版本闸（过期报 `FS_STALE_VERSION`）、`fs/write-intent` / `fs/edit-intent` 单槽 waterfall 决策点。自造一套 hash-CAS 只会多一个无法证明正确性的第二实现。

**代价**：宿主不替你重试，`FS_STALE_VERSION` 的处理仍在 sage-mem 这一侧；跨进程保证边界仍需公开说明。

**落地（0.9.19 实现，0.9.20 修正一处漏）**：

决定本身落地了，但第一版**漏了最关键的一步**：调的是 `writeText(target, content)`，`expected` 是空的。
而 `fs/write-intent` 只为「工具发起」的写入派发（插件自己写时一次都不发，实测），
所以 autodream 那条路**完全不设防** —— 守卫根本没被传下去，冲突记录也就永远不可达。

**这条教训比决定本身更该记**：当时的假 `writeText` **无条件抛错**、**从不检查 `expected` 传没传**，
于是套件全绿。**「测试通过」不等于「功能成立」** —— 与 0.9.17/0.9.18 漏登记两个套件是同一类病。
现在假 fs 会**记录**它收到的 `expected`，三条断言钉死「存在 → replaceIfVersion / 不存在 → createIfAbsent /
探不到 → 不传」，并做过变异验证（去掉守卫 → 2 条红）。

**另一处修正**：`expected` 由**我们自己** `stat` + 判定表算出（复用 `write-gate.js` 的
`decideWriteIntent`），不是另写一套「什么时候该传什么」的规则 —— 两条路的语义因此不会漂。
`stat` 失败时**不传**守卫，而不是退化成 `createIfAbsent`：后者对**其实存在**的文件是一次误拦。

## D19 · 回归基线重立（第二次），并在同一版给「注册窗口」加源代码守卫

**背景**：1.0.0 的评测报告发现 `test/eval/baseline.json` **已经不是当前行为的记录** ——
用它跑回归门得到的是「8 项改善、0 退化」。也就是说，那段时间里回归门比的是**更早的自己**，
它一直在说「无退化」，而那句「无退化」的意思是「没比旧版差」，不是「没比上一版差」。

**决定一：重立基线。** 依据是那 8 项全是改善、没有一项退化：

| 指标 | 旧基线 | 当前 |
|---|---|---|
| `recallAny` | 0.8406 | **0.8696** |
| `spanStrictRate` | 0.6170 | **0.6383** |
| `mrr` | 0.7403 | **0.7693** |
| `falseInjectRate`（越低越好） | 0.1408 | **0.0563** |

这与 D12 是同一条理由：**基线是「已知好」的参照，不是「曾经存在」的参照**。
不重立，回归门会在下一次真退化时依然可能说「无退化」。

**代价**：重立那一刻起，这 8 项改善被**冻结成新的默认**。以后要让某个指标变差换别的好处，
必须显式改基线并说明 —— 这道摩擦是有意的。

**决定二：给「写门的注册窗口」加源代码守卫。**
`docs/1.0.0-boundaries.md` 指出，写门在真实宿主里的**到达性**是本项目里最容易被误当保证的一条：
它在 CHANGELOG 的「行为变更」里、有 82 条断言、`npm test` 全绿 —— 而那些测的都是
**「判定对不对」**，它真实的失败方式是**「根本没被判」**。套件在**结构上**抓不到「注册被挪进
`ctx.inject`」这种改动（编译过、行为断言全绿、事件永远不来）。

所以在 `test/write-gate-wiring-test.mjs` 里加了 7 条**源代码级**断言：写门的注册必须在
`apply()` 里直接做、不得出现在 `ctx.inject(['fs'], …)` 或静态 `inject` 里、服务必须在处理器内部
用 `ctx.get('fs')` 取、以及那段「注册窗口」的警示注释必须留着。

**两个踩出来的细节**（都写进了测试注释）：
- 判「有没有做某件坏事」**必须先剥掉注释** —— 那警示注释里正写着反例写法，
  不剥就会把自己的警告当成违规（初版就这么红的）。
- 变异验证要挑**语法合法**的改法：第一次把大括号改坏，套件根本没跑到断言，
  那次「变异」什么也没证明。

**依据**：`docs/host-facts.md` 3.3 节（七组对照）、`docs/1.0.0-eval-report.md` 第 5 节。

## D20 · 全链性能：热点是 `scan`，**不是**排序；50 ms 阈值只对 30 份规模成立

**背景**：外部复审报告指出，原有性能数字只覆盖「分段 + 词元化 + 内存检索」，
**不含真实磁盘扫描的完整代价**，因此不能与 30 份语料的端到端结果拼成「1000 份端到端已验证」；
并要求「先测热点，再选索引方案」。`scripts/perf-chain.mjs` 就是为这件事写的。

**实测**（本机 Windows / Node v24，合成语料，**每档独立子进程**，20 个问题，各 8 段正文）：

| 规模 | 总字节 | scan 冷 | scan 热 | rank p50 / p95 | 全链 p50 / p95 |
|---|---|---|---|---|---|
| 30 | 20 KB | 13.46 ms | 15.48 ms | 0.14 / 5.35 ms | 12.28 / **15.89 ms** |
| 300 | 201 KB | 103.02 ms | 102.01 ms | 1.16 / 14.96 ms | 105.14 / **127.42 ms** |
| 1000 | 674 KB | 336.57 ms | 343.38 ms | 3.00 / 43.37 ms | 361.25 / **415.41 ms** |

**结论一：热点是 `scanMemoryFiles`，不是排序。** 1000 份时 scan 337 ms、rank 3 ms ——
**scan 占全链约 99%**。所以「先测热点再选方案」的答案是：**不要先上持久化索引**
（复审者也这么建议），该查的是「为什么每步组装都要重新扫一遍整个目录」。

**结论二：`50 ms` 这个阈值只在 30 份规模上成立。** 它是当初按「分段 + 记忆内检索」定的，
在 30 份时全链 p95 15.89 ms 有 3 倍余量；300 份就已经 **127 ms**、1000 份 **415 ms**。
**这不是「某个数字变慢了」，是阈值的适用域被写宽了。** 已如实记录，不再声称「1000 份也在阈值内」。

**结论三：此前那份「1000 文件 p95 21.64 ms」与本次相差约 19 倍，原因是口径不同** ——
它只量了分段/词元化/内存检索，没有真实磁盘扫描。两个数字都对，但**不能并列使用**。

**代价与代价之外**：本测量跑的是**手动调用 + 模拟 ctx** 的全链，
不含真实宿主注册、会话持久化与模型调用 —— 它比「只量排序」强，比「真实宿主端到端」弱。
这个分层必须写清楚，否则又是拿弱证据当强证据。

**一个必须记下来的过程教训**：本脚本初版在同一进程里换目录再 `import`，
但 `config.js` 的 `MEMORY_DIR` 是**模块顶层**读的，传递依赖不会重新求值 ——
于是第二、三档扫的还是第一档那个已被删掉的目录，`scan` 只花 0.3 ms、注入 0 条，
**打出一行「规模越大反而越快」的漂亮数字**。现在每档独立子进程，并且加了自检：
扫到的文件数不等于预期就整档报错，**绝不打印可疑数字**。

**下一步（未做）**：按 D2 的理由，仍不建持久索引；先查 scan 的重复代价能否用
「目录状态（名单 + mtime/size）缓存 + 失效判据」在进程内消掉，并单测失效正确性。

## D5 · 宿主可选能力用 `ctx.inject(deps, cb)` 挂子 fiber，**不用** `static inject`

**决定**：0.9.16 注册 `search_memory` / `read_memory` 时，用 `ctx.inject(['tools'], (inner) => { ... })`；**不**给 `MemoryGateway` 加 `static inject = ['tools']`。

**依据**（两份可复核的官方材料）：
1. `plugin-write` 技能的 `references/service-plugin.md`：**「`inject` lists required services. When a service is missing, the plugin waits for every declared service instead of loading... **Do not declare optional dependencies in `inject`; query them at the use site with `ctx.get('name')` and guard a missing result.」**
2. `dsh-official-ops` 的事后分析 `0001-acp-default-export-drops-inject`：**「对于插件机会性读取但未在 `static inject` 中声明的服务，使用 `ctx.get(name)`，绝不使用 `ctx.<name>`」**——属性代理只向祖先方向遍历，经由 shadow 边界会失败，而 `ctx.get` 是拓扑无关的查找。
3. `ctx.inject` 的既有用法先例：`dsh-mcp-client` 用 `ctx.inject(['mcpResources'], (inner) => inner.mcpResources.register(...))` 做可选接入。

**为什么不能简单用 `ctx.get('tools')`**（`host-facts` 探针实测，2026-10-15，headless profile）：
- 不声明 inject 的插件在**树还很浅时就被 `apply`**（当时 `props` 只有 24 条 / 8 个 service，`tools` 尚未提供）；
- 那一刻 `ctx.get('tools')` 返回 `undefined`，而插件**不会重跑** → 工具永远静默注册不上；
- 直接读 `ctx.tools` 则抛 `cannot get property "tools" without inject`。

**代价**：需要验证「在子 fiber 上 `register` 出来的工具，作用域是否覆盖到 agent」。

**已验证（2026-10-15，本机 headless profile，`scripts/tools-probe.mjs`）**：

```
registerOk: true          registerReturnsDisposer: true
registered:        ["search_memory","read_memory"]
visibleInSchemas:  ["search_memory","read_memory"]      ← 宿主眼里真的有这两个工具
execute: { isError:false, hasValue:true,
           valueKeys:["ok","scope","cursor","coverage","hits","nextCursor"],
           contentBlocks:1 }                            ← 走宿主自己的 dispatch，不是只看 schema
```

第三行最要紧：**schema 对不代表 dispatch 对** —— 参数 schema 与 `execute` 的期望不一致时，
只有真调一次才露得出来。探针因此既注册、又真调一次。

⚠️ 探针自己用的是**硬 `inject: ['tools']`**（它要确保拿得到服务），而 **sage-mem 主插件用的是
`ctx.inject` 子 fiber** —— 两者不同是有意的，别照抄探针的写法到主插件上。

### 例外与判据（0.9.19 实测补充，**这条比上面那段更要紧**）

上面那条规则有个例外，而且是**静默失效**型的例外，所以必须写明：

`fs/write-intent` / `fs/edit-intent` **不能**用 `ctx.inject` 挂。它们有一个**注册窗口**，
窗口在 fs 服务就绪**之前**就关了：

| 挂法 | 收到次数 |
|---|---|
| 不声明 inject、`apply()` 里直接挂 | **1** ✅ |
| 顶层 `inject:['fs']` | **0** |
| 顶层 `inject:['tokenMeter']` | **0**（与 fs 无关，是时机问题） |
| `ctx.inject(['fs'], sub)` 子 fiber | **0** |
| 不 inject、但 `apply()` 之后 2.5 秒再挂 | **0** |

**判据**（下次遇到新服务时照这个分，不要凭感觉）：

- **要先拿到服务才能做一次动作**（注册工具、读一次配置）→ 用 `ctx.inject(deps, cb)`。
  晚一点没关系，**不会漏**。
- **是一个「错过就永久错过」的事件流**（如 `fs/write-intent`）→ **`apply()` 里直接 `ctx.on`**，
  服务在**处理器内部**用 `ctx.get('fs')` 取。实测这样拿得到
  （`{hasFs:true, hasStat:true}`）—— 因为处理器是**之后**才跑的，那时树早就建好了。
- **分不清** → 先用探针数事件到达率（`scripts/host-facts-probe.mjs` 的模式 A/B 对照），
  别靠推理。这条例外就是这么发现的。

**代价**：直接 `ctx.on` 意味着「服务没了也不会自动摘掉监听器」—— 所以处理器内部必须自己容错
（`ctx.get` 拿不到就退化成「不管」），而不是假设服务一定在。

**证据**：`docs/host-facts.md` 3.3 节；七组对照在 `scripts/host-facts-probe.mjs`；
`sage-mem` 侧的接线注释在 `lib/index.js` 的写门注册处（那里有一份更短的警示）。

## D6 · 意图识别不做分类器

**决定**：用保守规则 + 明确理由枚举；不确定就不抑制。

**依据**：《同类设计取舍与改进计划》§3.2 论证了「高包含度就抑制」「有问号就激活」都不能当全局规则（核实 / 更正 / 解释历史三种意图可能同样高度相似）。

**代价**：会有漏判，即「该抑制时没抑制」，表现为多花一点上下文，而不是答错。

## D8 · 正文检索带相关性门槛（四条件）

**决定**：`rankChunks` 默认施加四条门槛：权重覆盖率 ≥ 0.35、绝对信息量 ≥ 1.5、
**至少一个命中词元够冷门**（`df ≤ 1` **或** `df/N ≤ 0.10`）、**连续命中词元数 ≥ 2**。
第三、四条都是析取/组合的一部分，单独用任何一条都不够。

**为什么要门槛**：BM25 对**任何**问题都能给出非零分——中文语料里「怎么」「什么」这类词元到处都是，于是「分数 > 0」约等于「总有结果」，无关问题会从「什么都不注」变成「注一堆噪音」。

**为什么第三条必须析取**：`df/N` 在小语料上失真。第一版只用比值时，**只有 5 份记忆的目录里真命中被全部滤掉**（全库独一份的词元算出来也是 0.2）——端到端实跑发现的回归。

**为什么需要第四条**（由真实评测集数据推出，不是推演）：无关问题「明天会不会下雨」把 7 份记忆拉进了上下文。诊断：

```
query 词元: 明天(df=0) 天会(df=1) 会不(df=0) 不会(df=7) 会下(df=0) 下雨(df=0)
命中的是：`不会`（真虚词，6.7%，低于 10% 的冷门线 → 被判"够冷门"）
          `天会`（跨词边界假词元，来自「那一天**会**缩短」，df=1 → IDF 最大）
```

中文双字词元必然造跨词假词元，而假词元因为"稀有"在 IDF 上最占便宜。连续性治它：巧合通常孤立（run=1），真实内容词通常连成片段（`连接池` run=2）。

**依据**：
- 对抗性扫参（16 份合成语料，4 份故意塞满通用词）：无门槛 4/12 无关题误召回 → 三条件 **1/12** → 四条件 **0/12**。
- 真实注入链（评测集 79 题）：无关题误召 **1/10 → 0/10**，应注入的文件级召回 **87.0% → 84.1%**。

| 门槛 | 相关题留住 | 无关题误召回 |
|---|---|---|
| 无门槛 | 12/12 | 4/12 |
| 只 ratio | 12/12 | 4/12 |
| ratio + sum | 12/12 | 1/12 |
| + 冷门 ≤ 0.15 | 12/12 | 1/12 |
| + 冷门 ≤ 0.10 | 12/12 | 0/12（另有用例仍未挡住，见 D8 第四条） |
| + 冷门 ≤ 0.05（只看比值） | 0/12 | 0/12 |

**代价**：
- 四个常量是在**小语料**上定的，真实语料的 df/N 量级不同，`scripts/eval-retrieval.mjs` 要在真实量级上复核一次再定稿。
- 第四条会拦掉「单个孤立双字命中」，典型是两字专名单独命中（**2.9 个百分点的召回**）。
  选择默认严格，因为「无关问题零误召」是硬验收项；补救办法是 0.9.16 的 `intent.js`：
  用户明确在问自己历史时放宽到 `minRun: 1`。
- 要放宽用 `rankChunks(..., { minEvidence: { minRun: 1 } })` 或 `{ minEvidence: false }`，别改常量。

## D11 · 摘要命中与正文命中取**并集**

**决定**：注入候选 = 摘要命中（在前）∪ 正文独有命中（在后），按文件去重。

**驳回的中间方案**：「摘要命中就只用摘要，一条都没有才轮到正文」。

**依据**：评测数据推翻。摘要只要命中任何一条（哪怕很弱、甚至命中错的文件），正文里那份真正相关的就再也没有机会——应注入的文件级召回从 **87.0% 掉到 60.9%**，而噪音并没有因此更低（正文命中本来就要过 D8 的四条门槛，实测误召回 1/10，与保守写法持平）。

**代价**：每步注入的条数变多，会话预算消耗更快。0.9.16 的预算池（baseline 保底 15–30%）要处理「baseline 与正文命中争额度」这件事。

## D9 · `baseline` 记忆不吃段落替换

**决定**：`baseline: true` 的记忆始终注入文件开头，即使问句命中了它的某一段也不换成段落。

**依据**：baseline 的语义是「每场会话都该**完整**在场」（你是谁、待办清单）。换成段落等于把它偷偷降级成「命中在场」，那正是 baseline 要防的事。

**代价**：baseline 命中某个细节时，注入的不是最相关那段，而是开头。用 baseline 本身的定位（短、必读）来承担。

## D10 · `chunk.id` 撞车时追加 `~n`

**决定**：`chunkFile` 里对 id 做去重，常见情形保持 `file.md#3-9` 的可读形式，撞车时追加 `~1`、`~2`。

**依据**：「单行超长」那条路径会把一行按字符切成多片，而它们**共享同一个行号** → 光用行号当 id 会撞车（实测一份含 5000 字符单行的文件产出 9 个片段，去重后只剩少数几个）。撞车会让「按 id 取回某一段」取到错的那片。由 `retrieval-tests` 在断言阶段发现。

## D13 · 由 `retrieval-tests` 断言阶段发现并修掉的三条模块缺陷

记进来是因为它们都属于「光看代码看不出来」的那类。

| # | 缺陷 | 为什么危险 |
|---|---|---|
| 1 | `retrieve()` 的 summary 一路候选池 = `limit + cursor`（与本页窗口同宽） | `nextCursor` 恒为 `null`、`candidates` 恒等于本页条数 —— **翻页根本翻不动**，而且调用方拿到的是一个自信的错误答案（「没有下一页」）。调用方改法：池宽必须大于窗口，用 `Infinity` 取满再切。 |
| 2 | `summaryHits` 的 `matchedBy` 在「三个字段谁都没单独命中」时回落成 `['description']` | 打分是**三字段去标点拼串后**算双字，跨字段边界也能命中。回落成 `description` 是**谎报命中原因**，展示层会据此给出错的解释。改成 `['summary']`。 |
| 3 | `sum ≥ 1.5` 在小语料误杀 | `sum` 用 IDF，而 IDF **随语料规模对数增长** —— 与 `ratio` 犯的是同一个错（D8 第三条已经析取过一次，`sum` 没跟上）。单段语料里原样命中 `FS_STALE_VERSION` 四个词元才 1.15，被整条滤掉。加逃生口：`df ≤ 1` 且 run 达标时不再看绝对量。 |

## D14 · 版本号从 0.9.15 跳到 0.9.16

**事实**：0.9.15 发布约 30 分钟后被 `npm unpublish`，同一份内容（含脱敏修复）改以 **0.9.16** 发布。

**为什么**：0.9.15 是**没跑发布前脱敏就推上去的** —— 公开仓库的文件里带了内部称呼与本机路径
（含一处随 npm 包发出的注释）。发现时仍在 unpublish 的 72 小时窗口内，所以选了「真删 + 重发干净版」，
而不是「留着一个已知不干净的版本、靠下一版覆盖」。

**代价**：版本号烧掉（npm 不允许重用已 unpublish 的版本号），原定 0.9.15 起的四版分批**整体后移一位**：

| 原编号 | 现编号 | 内容 |
|---|---|---|
| 0.9.15 | **0.9.16** | 正文段落检索 + 评测基座 + 宿主事实断言 |
| 0.9.16 | 0.9.17 | 原生检索工具 + 缺口状态卡 + 60 KB 两本账 |
| 0.9.17 | 0.9.18 | 台账 v2 + `tools/result` 观测 + 任务检查点 |
| 0.9.18 | 0.9.19 | 写入门接 `fs/*-intent` + 冲突队列 |

**纪律**（这次踩出来的）：`git push` 到公开远端**本身就是发布动作**，四查要在 push **之前**跑。
顺序反了，就只能走「重写历史」这条更贵的路 —— 而 reflog 与悬空对象不会立刻回收，
force-push 并不等于「抹掉了」。

## D15 · `decideDelivery` 已接进注入链，但**故意不开**「同 revision 抑制」

**决定**：注入链的交付决策交给 `decideDelivery`（渲染与决策分开），但 `visibleRevisions` 传**空集**。

**为什么接**：不接的话，「展示层分离」就只是纸面的 —— 同样的规则会同时活在 `lib/index.js`
的预算循环与 `deliver.js` 里，两份迟早漂。接进去之后，理由枚举（`baseline` / `evidence_missing` /
`budget_omitted` / …）成了可诊断的真实数据，而不是注释里的说法。

**为什么不开抑制**：`decideDelivery` 的抑制键是**文件 revision**（内容 hash）。而换一个问题
往往会命中**同一份文件的另一段** —— 按文件级 revision 抑制会把那段新的、正相关的内容一起挡掉。
要启用它得先有「段落身份」这个键（`chunk.id` + revision），并且单独评测一次。
**这是有意的保守，不是遗漏**；`deliver.js` 里那条规则与它的测试都保留着。

**代价**：同一份记忆在不同问题下可能被重复注入（内容不同，不完全是重复）。若以后实测发现
重复字节显著，就按「段落身份」键启用抑制。

## D16 · baseline 的预算保护用**排序**实现，不另设配额池

**决定**：不实现「baseline 保 15% B、上限 30% B」那套配额池；baseline 的预算优先权由
**候选顺序**（baseline 永远排在检索结果之前）保证。

**依据**：配额池要解决的是「baseline 被后面的候选挤掉」。而候选是按顺序进预算的，
baseline 排在最前 —— 除非它自己就超过正文池，否则不可能被挤掉。再叠一层配额池等于
给同一件事写两份实现，而且多一组要维护和评测的阈值。

**代价**：baseline 自己过大时会吃掉正文池的大部分（`MAX_BASELINE = 8` 是它的上限）。
若以后实测发现「baseline 太多导致任务证据进不来」，再加配额池 —— 那时它才是解决真问题的。

## D17 · 摘要侧加相关性门槛，且判据按**语料 IDF 尺度归一**

**决定**：`selectRelevant` 默认施加证据门槛，判据是 `命中词元的 IDF 绝对和 ≥ 0.6 × idfOf(1, N)`
（分母 = 这套语料里**单个词元能提供的最大权重**），且语料小于 8 份时不设门槛。

**问题**（真实目录实测）：中文里「怎么」「什么」这类词元在大量 `description` 里都有，一句
完全无关的「今天天气怎么样」靠一个「怎么」命中 **14 份**记忆、一次注入近 30 KB —— 而它们
全都卡在同一条分数线上（中位数 = 最高值），排序完全分不出来。

**为什么不用绝对阈值**（同一个坑的第三次）：`idf` 随语料规模**对数增长**。
- 绝对 `sum >= 1.5` 在百份量级的目录里等于「命中一个约四分之一文件都有的词元就放行」，
  门槛形同虚设；
- 同一批真命中在 2 份的小目录里又会被全杀掉（`idf(df=1)` 只有 0.69）。

**效果实测**：

| 指标 | 门槛前 | 门槛后 |
|---|---|---|
| 真实目录里无关问题的候选数 | 46 | **7** |
| 离线评测 Recall@5 | 58/69 = 84.1% | **60/69 = 87.0%** |
| 离线评测段落严格命中 | 29/47 = 61.7% | **30/47 = 63.8%** |
| 离线评测误注入（黑名单） | 10/71 = 14.1% | **4/71 = 5.6%** |

**召回也涨了这件事值得记**：被门槛清掉的弱摘要候选原先在**挤占前 5 名的名额**，把更好的正文命中
挡在外面。这也是为什么**只量摘要一侧会得出错误结论**（单看摘要一路，相关题从 37/69 掉到 29/69，
看上去是纯亏；量端到端才发现是净赚）。

## D18 · 台账路径必须跟着「它所依据的那个记忆目录」走

**事实**：`flushAccess(memoryDir)` 是「按 `memoryDir` 回收死键 → 把结果写回台账」。而台账路径原本
写死成模块常量 `ACCESS_LEDGER_FILE`。于是当调用方传入**别的**目录时，就是「扫描 A 目录、把结果写进
B 台账」—— **A 里不存在的名字在 B 台账里全被判成死键删掉**。

**怎么发现的**：真实状态根 `access.json` 从百来条真实记忆变成了两条夹具名（`a.md` / `b.md`）。
回溯到一次全量 `npm test`。

**完整因果链**（三层，缺一层都不会出事）：
1. DSH 进程本身带着 `SAGE_MEM_DIR`（指向真实记忆目录），**子 shell 继承它**；
2. `ad-smoke.mjs` 用**静态** `import` → 被提升到环境变量赋值之前 → `config.js` 已按真实目录加载完；
3. 它跑 autodream，而 autodream 跑前强制 flush 台账，传的是自己的**临时** memoryDir。

**修复**（三处，都要）：
- `access.js` 新增 `ledgerFileFor(memoryDir)`：用默认目录仍走 `STATE_ROOT`（尊重 `SAGE_MEM_STATE_DIR`），
  传别的目录则台账跟着那个目录走。`readAccessLedger(file)` 也接受路径。
- `engine.js` 读台账时传 `ledgerFileFor(this.memoryDir)`，与写对称。
- `test/run.mjs` 给**每个**子套件一套沙箱环境（临时 `SAGE_MEM_DIR` / `SAGE_MEM_STATE_DIR` / `DSH_HOME`），
  这样将来任何新套件都不可能碰到真实目录 —— 包括静态 import 的那些。

**影响面（已查，不夸大）**：用户的 autodream 配置是 `apply: false` + `autoArchive: 'report'`，
**只出报告、不动文件**，所以没有任何记忆因此被删。台账是**可重建的缓存**（记录「上次被注入」），
它会在后续会话中自己长回来；在此之前，自动归档的**候选建议**可能偏保守（把不常读的记忆算得更旧）。

**为什么生产不受影响**：生产两条调用路径传的都是 `MEMORY_DIR` 本身，`ledgerFileFor` 返回的仍是
`ACCESS_LEDGER_FILE`。这个坑只对「传了别的目录」的调用方成立 —— 也就是测试。
