# sage-mem 设计决定记录

**用途**：1.0.0 的最后审查要求「每条决定可追溯」——包括**被驳回的方案**。
每条记三样：决定了什么、依据是什么（要能复核）、代价是什么。

比更早的版本（0.9.16 之前）的取舍见 git 历史与 README。

---

## D1 · 台账不改成「每事件一文件」

**决定**：`access.json` 保持单文件，做 schema v2 扩展而不是拆成 `access-events/<uuid>.json`。

**驳回的方案**：《sage-mem 主动记忆实施方案》§6.2 建议每个事件写独立文件，理由是「避免多个进程同时覆盖一张共享 access.json」。

**依据**：
- sage-mem 是**单宿主进程**内运行，且已有进程内串行写队列（`lib/memory/access.js` 的 `enqueueFlush`）。
- 按「候选曝光」粒度写事件文件，每次 assemble 最多 10 条候选 × 每步 = 文件数爆炸。
- 稿子自己也把事件日志压缩列为「后续」。

**代价**：真要支持多进程并发写时，需要重新设计。届时再谈，不预先付这个复杂度。

---

## D2 · 段落检索不建持久索引

**决定**：段落与词频表只存在进程内存里，按文件 revision 缓存；记忆目录里不产生任何派生文件。

**依据**（真实记忆目录实测）：

| 指标 | 值 |
|---|---|
| 段落数 | 千级 |
| 冷启动（切段 + 词元化，进程内一次） | 约 80 ms |
| 热路径（重算 revision + 语料统计） | 约 2 ms |
| 单次正文检索（中位） | 约 4 ms |

预设门槛是「P95 > 50 ms 才加缓存层」，实测远低于。

**代价**：进程冷启动付一次约 80 ms；堆占用数十 MB。规模增长（比如上千份记忆）后要重新评估。

---

## D3 · 反馈排序（热度）默认关闭

**决定**：只记台账、不参与排序；连「近分打破平局」也先关。

**依据**：《同类设计取舍与改进计划》§3.1 指出调研报告的是「特定热度方案会压低老约束排名」，不能推出所有加权方式都失败，但也不能反向假设加法安全。启用必须有含「老约束 + 低曝光记忆」的评测集证明不退化。

**代价**：台账暂时只有诊断价值。

---

## D4 · 写入门接宿主 `fs` 的版本闸，不自造 CAS

**决定**：autodream 的自动改写改用 `ctx.fs.writeText(..., { kind: 'replaceIfVersion', version })`，用返回的 `{operation, version, before, after}` 当收据。

**依据**：宿主 `fs` 已提供原子发布与版本闸（过期报 `FS_STALE_VERSION`）、`fs/write-intent` / `fs/edit-intent` 单槽 waterfall 决策点。自造一套 hash-CAS 只会多一个无法证明正确性的第二实现。

**代价**：宿主不替你重试，`FS_STALE_VERSION` 的处理仍在 sage-mem 这一侧；跨进程保证边界仍需公开说明。

---

## D5 · 宿主可选能力用 `ctx.inject(deps, cb)` 挂子 fiber，**不用** `static inject`

**决定**：0.9.16 注册 `search_memory` / `read_memory` 时，用 `ctx.inject(['tools'], (inner) => { ... })`；**不**给 `MemoryGateway` 加 `static inject = ['tools']`。

**依据**（两份可复核的官方材料）：
1. `plugin-write` 技能的 `references/service-plugin.md`：**「`inject` lists required services. When a service is missing, the plugin waits for every declared service instead of loading... **Do not declare optional dependencies in `inject`; query them at the use site with `ctx.get('name')` and guard a missing result.」**
2. `dsh-official-ops` 的事后分析 `0001-acp-default-export-drops-inject`：**「对于插件机会性读取但未在 `static inject` 中声明的服务，使用 `ctx.get(name)`，绝不使用 `ctx.<name>`」**——属性代理只向祖先方向遍历，经由 shadow 边界会失败，而 `ctx.get` 是拓扑无关的查找。
3. `ctx.inject` 的既有用法先例：`dsh-mcp-client` 用 `ctx.inject(['mcpResources'], (inner) => inner.mcpResources.register(...))` 做可选接入。

**为什么不能简单用 `ctx.get('tools')`**（`host-facts` 探针实测，2026-10-15，headless profile）：
- 不声明 inject 的插件在**树还很浅时就被 `apply`**（当时 `props` 只有 24 条 / 8 个 service，`tools` 尚未提供）；
- 那一刻 `ctx.get('tools')` 返回 `undefined`，而插件**不会重跑** → 工具永远静默注册不上；
- 直接读 `ctx.tools` 则抛 `cannot get property "tools" without inject`。

**代价**：需要验证「在子 fiber 上 `register` 出来的工具，作用域是否覆盖到 agent」。这是 0.9.16 的真实宿主验证项，用 `scripts/host-facts-probe.mjs` 同一套路数取证。

## D6 · 意图识别不做分类器

**决定**：用保守规则 + 明确理由枚举；不确定就不抑制。

**依据**：《同类设计取舍与改进计划》§3.2 论证了「高包含度就抑制」「有问号就激活」都不能当全局规则（核实 / 更正 / 解释历史三种意图可能同样高度相似）。

**代价**：会有漏判，即「该抑制时没抑制」，表现为多花一点上下文，而不是答错。

---

## D7 · 明确不做

| 项 | 依据 |
|---|---|
| embedding / 向量库 / 常驻服务 / worker / SQLite 主库 | 方向稿 §6 硬约束：纯文件、零依赖、可 diff、可 git、可手编 |
| 每轮子代理蒸馏、技能自动晋升 | 《同类设计取舍》§2 自己列为「暂不采用 / 推迟」 |
| 每事件一文件台账 | 见 D1 |
| 自造 CAS / 多文件事务 / 跨进程锁协议 | 见 D4 |
| 「用引用替代旧摘要」 | 宿主 `system-prompt/assemble` 返回的 `contexts` 是**逐条追加**为持久消息（`source.kind === 'plugin'`），没有替换语义 |
| CLI（`tools/memory-cli.mjs`）与「主题目录 Markdown 降级」 | 宿主原生提供 `ctx.tools.register`，降级路径没有必要 |

## D8 · 正文检索带相关性门槛（四条件）

**决定**：`rankChunks` 默认施加四条门槛：权重覆盖率 ≥ 0.35、绝对信息量 ≥ 1.5、
**至少一个命中词元够冷门**（`df ≤ 1` **或** `df/N ≤ 0.10`）、**连续命中词元数 ≥ 2**。
第三、四条都是析取/组合的一部分，单独用任何一条都不够。

**为什么要门槛**：BM25 对**任何**问题都能给出非零分——中文语料里「怎么」「什么」这类词元到处都是，于是「分数 > 0」约等于「总有结果」，无关问题会从「什么都不注」变成「注一堆噪音」。

**为什么第三条必须析取**：`df/N` 在小语料上失真。第一版只用比值时，**只有 5 份记忆的目录里真命中被全部滤掉**（全库独一份的词元算出来也是 0.2）——端到端实跑发现的回归。

**为什么需要第四条**（由真实评测集数据推出，不是推演）：无关问题「明天会不会下雨」把 7 份记忆拉进了上下文。诊断：

```
query 词元: 明天(df=0) 天会(df=1) 会不(df=0) 不会(df=7) 会下(df=0) 下雨(df=0)
命中的是：`不会`（真虚词，6.7%，低于 10% 的冷门线 → 被判"够冷门"）
          `天会`（跨词边界假词元，来自「那一天**会**缩短」，df=1 → IDF 最大）
```

中文双字词元必然造跨词假词元，而假词元因为"稀有"在 IDF 上最占便宜。连续性治它：巧合通常孤立（run=1），真实内容词通常连成片段（`连接池` run=2）。

**依据**：
- 对抗性扫参（16 份合成语料，4 份故意塞满通用词）：无门槛 4/12 无关题误召回 → 三条件 **1/12** → 四条件 **0/12**。
- 真实注入链（评测集 79 题）：无关题误召 **1/10 → 0/10**，应注入的文件级召回 **87.0% → 84.1%**。

| 门槛 | 相关题留住 | 无关题误召回 |
|---|---|---|
| 无门槛 | 12/12 | 4/12 |
| 只 ratio | 12/12 | 4/12 |
| ratio + sum | 12/12 | 1/12 |
| + 冷门 ≤ 0.15 | 12/12 | 1/12 |
| + 冷门 ≤ 0.10 | 12/12 | 0/12（另有用例仍未挡住，见 D8 第四条） |
| + 冷门 ≤ 0.05（只看比值） | 0/12 | 0/12 |

**代价**：
- 四个常量是在**小语料**上定的，真实语料的 df/N 量级不同，`scripts/eval-retrieval.mjs` 要在真实量级上复核一次再定稿。
- 第四条会拦掉「单个孤立双字命中」，典型是两字专名单独命中（**2.9 个百分点的召回**）。
  选择默认严格，因为「无关问题零误召」是硬验收项；补救办法是 0.9.16 的 `intent.js`：
  用户明确在问自己历史时放宽到 `minRun: 1`。
- 要放宽用 `rankChunks(..., { minEvidence: { minRun: 1 } })` 或 `{ minEvidence: false }`，别改常量。

## D11 · 摘要命中与正文命中取**并集**

**决定**：注入候选 = 摘要命中（在前）∪ 正文独有命中（在后），按文件去重。

**驳回的中间方案**：「摘要命中就只用摘要，一条都没有才轮到正文」。

**依据**：评测数据推翻。摘要只要命中任何一条（哪怕很弱、甚至命中错的文件），正文里那份真正相关的就再也没有机会——应注入的文件级召回从 **87.0% 掉到 60.9%**，而噪音并没有因此更低（正文命中本来就要过 D8 的四条门槛，实测误召回 1/10，与保守写法持平）。

**代价**：每步注入的条数变多，会话预算消耗更快。0.9.16 的预算池（baseline 保底 15–30%）要处理「baseline 与正文命中争额度」这件事。

## D9 · `baseline` 记忆不吃段落替换

**决定**：`baseline: true` 的记忆始终注入文件开头，即使问句命中了它的某一段也不换成段落。

**依据**：baseline 的语义是「每场会话都该**完整**在场」（你是谁、待办清单）。换成段落等于把它偷偷降级成「命中在场」，那正是 baseline 要防的事。

**代价**：baseline 命中某个细节时，注入的不是最相关那段，而是开头。用 baseline 本身的定位（短、必读）来承担。

---

## D10 · `chunk.id` 撞车时追加 `~n`

**决定**：`chunkFile` 里对 id 做去重，常见情形保持 `file.md#3-9` 的可读形式，撞车时追加 `~1`、`~2`。

**依据**：「单行超长」那条路径会把一行按字符切成多片，而它们**共享同一个行号** → 光用行号当 id 会撞车（实测一份含 5000 字符单行的文件产出 9 个片段，去重后只剩少数几个）。撞车会让「按 id 取回某一段」取到错的那片。由 `retrieval-tests` 在断言阶段发现。

## D12 · 0.9.16 重立了评测基线

**事实**：`test/eval/baseline.json` 在 2026-10-15 被重新记录过一次。

**依据**：D8 的第四条门槛（连续命中 ≥ 2）是**有意的行为变更**，旧基线记的是它之前的行为，
于是回归门报了 6 项「退化」——那不是回归，是取舍。按 `test/eval/README.md` 文档化的流程重立：
`node scripts/eval-retrieval.mjs --mode all --json test/eval/baseline.json`，复验 `--baseline` 退出码 0。

**这次行为变更的代价（已公开在上表）**：`recallAny` 0.8696 → 0.8406、`spanStrictRate` 0.6809 → 0.6170；
换来 `overInjectRate`（无关问题仍注入）0.5000 → **0.1000**。判据是 D8：无关问题零误召是硬验收项。

**0.9.14 的历史对比仍可查**：`--mode summary` 的 50.7% 是旧行为，它不会因为基线重立而消失
（CHANGELOG 的对照表就是拿它比的）。

## D13 · 由 `retrieval-tests` 断言阶段发现并修掉的三条模块缺陷

记进来是因为它们都属于「光看代码看不出来」的那类。

| # | 缺陷 | 为什么危险 |
|---|---|---|
| 1 | `retrieve()` 的 summary 一路候选池 = `limit + cursor`（与本页窗口同宽） | `nextCursor` 恒为 `null`、`candidates` 恒等于本页条数 —— **翻页根本翻不动**，而且调用方拿到的是一个自信的错误答案（「没有下一页」）。调用方改法：池宽必须大于窗口，用 `Infinity` 取满再切。 |
| 2 | `summaryHits` 的 `matchedBy` 在「三个字段谁都没单独命中」时回落成 `['description']` | 打分是**三字段去标点拼串后**算双字，跨字段边界也能命中。回落成 `description` 是**谎报命中原因**，展示层会据此给出错的解释。改成 `['summary']`。 |
| 3 | `sum ≥ 1.5` 在小语料误杀 | `sum` 用 IDF，而 IDF **随语料规模对数增长** —— 与 `ratio` 犯的是同一个错（D8 第三条已经析取过一次，`sum` 没跟上）。单段语料里原样命中 `FS_STALE_VERSION` 四个词元才 1.15，被整条滤掉。加逃生口：`df ≤ 1` 且 run 达标时不再看绝对量。 |

## D14 · 版本号从 0.9.15 跳到 0.9.16

**事实**：0.9.15 发布约 30 分钟后被 `npm unpublish`，同一份内容（含脱敏修复）改以 **0.9.16** 发布。

**为什么**：0.9.15 是**没跑发布前脱敏就推上去的** —— 公开仓库的文件里带了内部称呼与本机路径
（含一处随 npm 包发出的注释）。发现时仍在 unpublish 的 72 小时窗口内，所以选了「真删 + 重发干净版」，
而不是「留着一个已知不干净的版本、靠下一版覆盖」。

**代价**：版本号烧掉（npm 不允许重用已 unpublish 的版本号），原定 0.9.15 起的四版分批**整体后移一位**：

| 原编号 | 现编号 | 内容 |
|---|---|---|
| 0.9.15 | **0.9.16** | 正文段落检索 + 评测基座 + 宿主事实断言 |
| 0.9.16 | 0.9.17 | 原生检索工具 + 缺口状态卡 + 60 KB 两本账 |
| 0.9.17 | 0.9.18 | 台账 v2 + `tools/result` 观测 + 任务检查点 |
| 0.9.18 | 0.9.19 | 写入门接 `fs/*-intent` + 冲突队列 |

**纪律**（这次踩出来的）：`git push` 到公开远端**本身就是发布动作**，四查要在 push **之前**跑。
顺序反了，就只能走「重写历史」这条更贵的路 —— 而 reflog 与悬空对象不会立刻回收，
force-push 并不等于「抹掉了」。
