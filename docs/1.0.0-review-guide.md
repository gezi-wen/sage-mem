# 1.0.0 复审材料包 · 入口

**给审查者**：这个仓库是一个 DSH 插件的 1.0.0 候选版本。你大概没有它的上下文，
所以这份入口只做三件事：**读什么、按什么顺序读、以及我们最希望你挑战哪里**。

## 读什么（三份，都是自包含的）

| 顺序 | 文件 | 它回答什么 |
|---|---|---|
| 0 | `1.0.0-review-response.md` | **上一轮复审九条的处置与复验方式** —— 先看这份，能省掉重复提问 |
| 1 | `1.0.0-boundaries.md` | **这东西到底靠不靠得住** —— 34 条能力逐条定性（保证 / 尽力 / 已知做不到 / 待验证），每条带依据与验证手段 |
| 2 | `1.0.0-contract.md` | **升级之后什么可以依赖** —— 公开面逐条写清「保证什么 / 不保证什么」，并列出明确不在契约里的东西 |
| 3 | `1.0.0-eval-report.md` | **数字到底是多少、以及这些数字测不到什么** —— 每条结论都可重跑 |

**外加两份背景**（想深挖时再看）：
- `decisions.md` —— 每个设计决定的理由**与被驳回的方案**。想知道「为什么不那样做」看这里。
- `host-facts.md` —— 宿主契约的**实测**事实（不是文档推的）。含我们踩过的坑与没能验证的部分。

## 最希望你挑战的五处

材料里写得最顺的地方，往往是最该被怀疑的地方。这五处是我们自己知道的薄弱点：

1. **「保证」的依据强度参差。** 我们的「保证」= 有断言或实测支撑，**不是形式化证明**。
   而断言可能测错东西 —— 这个项目**已经真实翻过两次车**：两个版本、126 条断言
   从没被运行过，而两版更新日志都写着「全绿」。请对每一条「保证」追问：
   **这条被断言测的是它自己吗？还是测了一个长得像它的东西？**
   （其中一处已经写进材料：写门在真实宿主里的**到达性**至今**没有回归断言**。）

2. **性能与召回数字的可迁移性。** 评测语料只有 30 份，且它的 `description` 是**为了让检索能命中而手写的** ——
   真实使用里摘要往往随意甚至缺失。我们认为可迁移的是**相对关系**（某些设计 A 明显优于 B），
   不可迁移的是**绝对值**。请专门压这个区分：**哪些结论换个语料就没了？**

3. **单点测量被当成对照的地方。** 材料里凡标「反向对照」的都是真的开/关对照过；
   凡标「单点测量」的意思是——**没有对照，别信它的因果**。请扫一遍看有没有漏标的。

4. **「已知做不到」里有没有藏着「能做到但没做」。** 我们把 9 条列为能力边界并给了取舍理由。
   请判断：这些理由成立吗？还是只是成本问题被写成了不可能？

5. **真实宿主实测的覆盖面不对称。** 探针**插件**只在 headless profile 上跑过；
   桌面版只跑过 Inspect 查询（读契约声明，另一条路径，**验不到「事件会不会到达」**）；
   网页版**两条都没有**。这条在边界表里标为「待验证」，但它可能影响前面所有结论的适用范围 ——
   尤其「事件到达性」那类结论，换个 profile 未必一样。

## 怎么独立复核（不需要我们这个环境）

```bash
npm test                     # 全部断言（含一条守卫：检查有没有「写了但从没跑过」的套件）
node scripts/eval-retrieval.mjs --mode all --baseline test/eval/baseline.json
node scripts/host-facts-probe.mjs   # 需要在 DSH 宿主里跑；文件头写了怎么挂
```

最后一条需要 DSH 宿主，其余两条纯 Node 即可。

## 材料的局限（先说清，免得你按它推出来的结论比它能支撑的更远）

- **它是我们自己写的。** 写材料的人和写代码的人是同一批，所以它天然倾向于把我们的取舍
  写得比实际更合理。请优先怀疑「**取舍理由**」，那是最容易自我美化的一段。
- **它不完整。** 边界表覆盖 34 条，但**没有**一个机制保证「该进表的都进了」——
  这和「套件登记守卫」是同一类问题，只是**这次还没有守卫**。
- **数字会过时。** 评测报告的口径是本版本。代码一改，绝对值就旧了；相对关系通常还在。
- **`docs/` 下的其余文档不是这份材料的一部分** —— 它们是开发过程中的记录，风格与时效性都不同。
