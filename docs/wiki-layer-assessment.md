# 第三层「wiki」要不要进 sage-mem（2026-11-10 评估）

> 触发：有人看到 Anthropic《The components of agent memory》（2026-11-06）里的第三层「记忆表示层 / wiki」，
> 问「sage-mem 用得到吗，会不会是减益」。
> 本文只给判定与代价，不动代码。

## 一、Anthropic 那套是什么

四个组件，不是四个"数据库"：

| 层 | 内容 | 产生方式 |
|---|---|---|
| ① 原始会话记录 | 输入 / 输出 / 工具参数与返回 | 自动 |
| ② 记忆笔记 | 会话中就地写的要点 | 模型判断重要性后写 |
| ③ **记忆表示层（wiki）** | 按主题成页、页间互链的**导航图** | **做梦**在离线时写与维护 |
| ④ 注入上下文 | 每场会话开头预加载的那一小块 | 做梦把笔记"提升"到顶层 |

第三层的原文定义：a collection of pages ... gathers what Claude knows about one subject and **links it to other notes. These links effectively provide Claude with a map**。所以它是**地图**，不是知识库。

它的收益是在什么尺度上量出来的：

- 语料 **35 万个文件 / 约 4.2 亿 token**；做梦跑 **128 场**；25 道题从 **13% → 48%** 达标率。
- **必须配搜索工具**才有最大收益：搜索+wiki 随 wiki 长大 **54% → 61%**，单独搜索 **53%**，单独 wiki **48%**；同时每题省约 **2 万 token**。
- **单文档就能答的题，wiki 无增益**（Harvey LAB 对照）。
- 失效形态：**wiki 长得比原始语料还大**（"地图与帝国同大"），等于什么都没抽象。
- 维护要算力；wiki 会积累错误与幻觉，需要反复做梦校正；doreaming 的节奏（多久跑一趟）原文列为**开放问题**。

两条与"加层"逆向的实测：

- Pokémon：**写 413 份笔记的输给写 9 份的**（前者频繁过期、后期 17 步全在整理记忆、没在玩游戏）。
- 给强模型写死"只记失败"这类规则，**性能反而掉了**；给方向、不给死规则更有效。

## 二、sage-mem 现状（2026-11-10 实测）

| 项 | 值 |
|---|---|
| 根目录记忆文件 | **126 条**，合计 **1569 KB** |
| 归档 | 55 条（不参与检索） |
| `MEMORY.md` | 47.8 KB / 155 行，且是 `NON_ENTRY_FILES` —— **完全不注入**，按需读 |
| 注入名额 | 10 条 × 1500 字符；单会话累计 60 KB；baseline ≤ 8 |
| 检索面 | `description` + `aliases` + 文件名，双字覆盖率 + IDF 归一门槛（0.6×`idf(1,N)`）；摘要无命中时用正文 BM25 段落兜底，两路取并集 |
| 已有"做梦" | `lib/autodream/`：合并重复、修索引、修断链、相对日期转绝对、全量快照 + 回滚 + 逐条缘由于报告 |
| 已有"纠错" | `valid_at` / `invalid_at` / `superseded_by`，注入侧按 `buildExpirySet` 抑制失效条目 |
| 已有"图" | `[[双链]]` + `MEMORY.md` 索引（人工/做梦维护） |

关键差别：**Anthropic 的注入层是索引（Claude Code 只读 `MEMORY.md` 前 200 行 / 25 KB），sage-mem 的注入层是检索结果，索引根本不进上下文。**

## 三、判定：作为"层"进来是净减益

四条理由，按杀伤力排：

1. **分母摊薄。** 检索是"所有文件的摘要面比一遍再取前 10"。多出来的每一页 wiki 都是新的检索靶子，而它的 `description` 必然与自己综述的那几条笔记高度重合 —— 命中被分票，真该端上去的那条被挤到第 11 名。记忆技能的"防膨胀纪律"（多一条新文件 ≈ 摊薄一次命中率）说的就是这个，wiki 是把分母**翻倍**而不是 +1。
2. **二手挤占一手。** 注入的 60 KB 是零和的。wiki 页是**派生内容**，端上去就少端一条原始笔记。Anthropic 自己的证据指向同一方向：注入层必须"相对小"，否则指令遵循度下降；笔记越多越差（413 vs 9）。
3. **双真相必然漂移。** 笔记被 `superseded_by` 收掉、被 autodream 合并、正文被改 —— wiki 页不会自动跟着变，而且它的失效**无提示**。这正是我们踩过多次的形态（AGENTS.md 与记忆两份口径、技能与代码两处数字）。原文也承认：wiki 会积累错误与幻觉。
4. **地图大于疆域。** 我们的语料 1.5 MB / 126 条，检索一遍是毫秒级、覆盖 100%，没有"够不着的角落"需要地图。真要按主题成页，页数与笔记数同量级，抽象掉的为 0 —— 就是原文那个反例。而维护它的算力我们没有：一趟做梦 = 一次模型跑批。

此外还有一条工程账：wiki 层要自带审计（页 ↔ 笔记漂移、孤儿页、悬空页），审计面每加一处就多一种"假绿灯"。我们已经在 `memory-audit.cjs` 上吃过"量具自己造假"的教训。

## 四、值得拿过来的三件事（低代价）

1. **只在密集簇上做 hub 页，不做全量 wiki。** 现有 126 条里有 3 个簇单簇 ≥ 8 条（DSH 插件生态 / sage-mem 自身 / guikit 与 GUI）。每个簇一张人工维护的**导航页**（回答"这个问题该读哪几条"），`type: reference`、`baselinePriority` 低、`description` 塞满该簇的口语别名。等价于把 `MEMORY.md` 的一组行扩成一段地图 —— **是索引的增强，不是新层**。
2. **做梦写回时"引文不综述"。** LAB 那个实验最值钱：多个 agent 同时写一张共享的合同条款表，57 条事实只剩 41 条；改成一个 agent 一页、逐字引用原文，57/57 保住。落到 autodream：**合并优先"链接 + 归档"，合并时对命令、路径、配置项必须逐字保留，不许改写成概括**。这条能直接减掉一类静默丢事实。
3. **第二趟做梦专门修悬空链与提升。** 笔记链接到还不存在的页、或该提升到顶层的小条目，交给第二趟做梦（我们的 `[[双链]]` 审计已经是第一趟的一半）。

## 五、怎么证而不是怎么辩

`scripts/eval-retrieval.mjs` 是现成的裁判（金标语料 + 问题集，离线、带分子分母）。判据：

1. 复制 `test/eval/corpus` 为影子语料，按簇加 hub 页；
2. 跑同一份 `questions.jsonl`，比 **Recall@5**、**段落严格命中**、**误注入**三个数；
3. 通过标准：三项**都不退化**，且至少一项改善 ≥ 3 个百分点；否则只保留第 4 节第 2、3 条（那是纯收益）。

只量摘要一侧会得出错误结论（`retrieval.js` 里记着上一回就是这么误判掉 8 个点的），必须量端到端。

## 六、2026-11-10 追加：用现有的 `tags` 当 hub 行不行（实测，不是推演）

提议：`tags` 字段已经在 UI 里（「列表页可按它筛」），让智能体给同一主题的多条记忆打同一个标签（如 `学习通作业`），是不是一个便宜版 hub？

探针跑了真实记忆目录（一个真实记忆库，124 条参与检索，已排除 `MEMORY.md` / `session-log.md`）：

**结论一：`tags` 现在对检索的贡献是 0。** 检索面是 `summaryHay()` = `description` + `aliases` + 文件名（`retrieval.js:83`），`tags` 不在里面；正文 BM25 也不读它。宿主侧 `parseTags` 解析出来后只喂给面板（`index.js:122/246` → `client.js` 的 `filter.tags`）。全目录 **0 条**记忆带 `tags`，所以「打标签就能被想起来」今天是错觉。

**结论二：「学习通作业」这个问法，整簇已经能召回。** 5 份内容文件全部命中：

| 分数 | 文件 | 命中词元 |
|---:|---|---|
| 1.000 | project_coursework-homework.md | 学习 习通 通作 作业 |
| 1.000 | reference_chaoxing-ueditor-submit.md | 学习 习通 通作 作业 |
| 1.000 | reference_chaoxing-workflow.md | 学习 习通 通作 作业 |
| 0.750 | user_courses-2026fall.md | 学习 习通 作业 |
| 0.500 | project_coursework-submissions.md | 学习 作业 |

所以「打 tag 才能把同一个主题串起来」这个前提，在这个例子上不成立 —— 串起来靠的是各文件 `description`/`aliases` 里碰巧都有「学习通」。

**结论三：真正的洞在「口语问法」。**

| 问句 | 摘要命中 | 实际相关的 | 后果 |
|---|---|---|---|
| 学习通作业 | 5 | 5 | 正常 |
| 实验报告怎么交 | **10** | 3 | 名额被 7 条噪音填满，整簇注入可达 **10 × 1500 字符 ≈ 45 KB**（UTF-8 中文，约 60 KB 预算的 75%） |
| 这周要交的东西 | 3 | **0** | 整簇消失，一条真的都没有 |

噪音为什么能过闸，量出来的：

- 门槛 = `0.6 × maxIdf` = `0.6 × 4.423` = **2.654**
- 单个双字的 idf：「报告」df=6 → 2.957、「实验」df=7 → 2.813、「作业」df=5 → 3.124、「学习」df=5 → 3.124
- **即：任何一个出现在 5~7 份文件里的普通双字，单靠它自己就超过门槛 106%~118%**。只有「怎么」（df=15，idf 2.087）确实被拦住 —— 当初那条修法对「今天天气怎么样」有效，但没有余量。

**结论四：tag 的价值不在检索，在另外三处。** UI 筛选、做梦按簇整理（「这 5 条是这个簇的」）、以及将来的**簇传导**（命中带 tag 的一份 → 补 ≤2 条同 tag 兄弟）。这三件 `aliases` 替代不了。

### 因此的顺序（不是一次性全做）

1. **先修门槛**（纯收益，今天就在伤人）：摘要面加「命中词元数 ≥ 2 **或** 命中一个 df ≤ 3 的稀有词元」。用上面这批真实数据验：真命中全保（5 条都命中 ≥2 词元）、噪音全清（每条只命中 1 个）。回归用 `scripts/eval-retrieval.mjs`。
2. **口语别名补齐**（0 代码）：簇内 5 份的 `aliases` 各补「交作业 / 这周要交的东西 / 实验报告怎么交」这类问法。`user_courses-2026fall.md` 现在连 `aliases` 行都没有。
3. **要 hub 就做 1 张导航页，不要 5 张**：一屏写清「状态→哪份 / 手法→哪份 / 逐次细节→哪份 / 课程入口→哪份」，`description`/`aliases` 装满口语问法。占 1 个注入名额，解的是「该读哪份」，`tags` 解不了这个。
4. **`tags` 等簇传导一起做**。只加 tag 不写传导逻辑 = 列表页多一个筛选项，还要另维护一张词表；两处都写（tag + aliases 同一句）就是又一份会漂移的真相 —— 选一处。
