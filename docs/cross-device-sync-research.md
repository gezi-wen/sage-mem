# 跨设备记忆：调研与验证（2026-11-03，**未实现**）

> 状态：**调研完成，实现暂缓**（决定见 `docs/decisions.md` 的 D34）。
> 本文记录「要解决什么问题、有哪些方案、为什么倾向某一个、实测到了什么」。

---

## 1. 目标场景

- 设备 A / B（笔记本、手机，**无固定在线时间**）与设备 C（**相对常在线**）。
- 三台设备在同一个 Tailscale 网络里。
- 把 sage-mem 的记忆目录在它们之间同步：可从 C 拉、可向 C 推；可自动、可手动。
- **C 不是一个纯服务器，它自己也会改记忆** —— 这是整个设计的难点。

约束：**不改变现有记忆系统的流程**。记忆文件仍是普通 `.md`，同步状态存在插件自己的状态目录里，不进记忆目录。

---

## 2. 为什么「按消息追加」的邮局模式不适用

同一套 agent-post 式的「签名消息 + 权威副本」能跨设备工作，靠四点：消息自包含、权威副本只存一处、**只追加不改写**、传输走 SSH。

记忆文件会被两端同时改写，而 append-only 世界里没有「同一个键被覆盖」这件事，所以它没有冲突。硬套只能退化成「整份正文塞进消息 + 最后写入者赢」。

**结论：可变文件需要的是「三方比较」，不是「消息队列」。**

## 3. 方案对比

| 方案 | 同步粒度 | 冲突策略 | 额外服务 | 适配度 |
|---|---|---|---|---|
| **Syncthing** | 文件→块，每文件版本向量 | 冲突副本 `<名>.sync-conflict-<日期>-<时间>-<设备>.<扩展名>`，**两份都留** | 无中心服务，每端一个 daemon | ★★★★☆ 三端全覆盖 |
| Unison | 文件（rsync 式差量） | 内置三方比较；冲突交互提问 | 无，ssh 直连 | ★★★☆ 无 Android |
| rsync | 文件（单向） | **无冲突检测** | 无 | ★ 双向必丢 |
| rclone bisync | 文件（双向） | 冲突后缀策略 | 无 | ★★☆ base 只存 size+modtime |
| git | 行/提交 | 三方 merge，冲突标记**写进文件** | C 上裸仓库 | ★★ 手机端不稳 |
| CRDT（Yjs/Automerge） | 字符级 | 自动合并永不冲突 | 需同步服务 | ★ **过度设计** |

### 为什么 CRDT 是过度设计

它解决「多人同时在同一文档里逐字符编辑」。本场景的并发是「几小时到几天一次、**整文件重写**」。把一条记忆变成 CRDT 文档，等于放弃纯文本可 grep / 可 diff / 可被模型直接读的全部优势，还要多维护一份二进制状态；而模型是整篇重写，落到 CRDT 上是把两篇不同观点的记忆交错编织成一篇——**比留两份更糟**。

### 为什么不能自动合并 markdown 正文

- 模型倾向整篇重写 → 改动区域几乎必然重叠
- 记忆文件是**状态断言**而不是散文：两份「当前状态」合并后是一份自相矛盾的文件，未来读它的人无法判断哪句为真
- frontmatter / YAML 被文本合并后可能结构损坏，而加载器会**静默丢弃**
- 合并会把「发生过冲突」这个事实本身抹掉 —— 而那恰恰是唯一能事后知道「那天有两套版本」的证据

**结论：冲突一律留两份，人工（或一个专门的模型）裁决；自动合并只能产出候选，两份原件必须都留着。**

## 4. 为什么不自研同步引擎

文件级双向同步要处理的问题（全部有真实事故来源）：

1. **「两边都有文件、没有共同祖先」时绝不能自动选** —— 所有按 mtime 挑一个的实现都是在这里开始丢数据
2. mtime + size 快检会漏掉「同一秒、同一长度」的改动
3. 「相等即不动」这个分支本身就是坑（同 mtime 同大小 = 静默跳过）
4. 时钟漂移会让新内容被判成旧内容
5. `cp` / 解压 / 从备份恢复会保留旧 mtime，于是新文件看起来最旧
6. 删除可能赢过修改（修改 vs 删除，删除获胜时被改名成冲突副本）
7. 大小写不敏感文件系统会撞名（Windows / macOS / 部分 Android）
8. Unicode 规范化（NFD ↔ NFC）会让文件名改变或撞名
9. base 提前推进 / 中途崩溃 = 无声丢失（必须 CAS + 对端确认后才推进）
10. base 放进被同步目录 = 自激（状态文件自己改自己）
11. 编辑器非原子保存 / 临时文件（`.swp` / `~` / `.tmp`）会被当正常文件同步
12. **冲突副本被下游消费方吃进去** —— 记忆索引必须排除 `*.sync-conflict-*`，否则模型会读到两套互相矛盾的记忆
13. 手机端 git 不可靠（移动端 Git 实现被作者自己标为 very unstable，不支持 SSH）
14. Unison 两端版本必须匹配

**这些坑已经被成熟工具踩了十几年。自研 = 拿用户的记忆当测试数据。**

## 5. 传输层对比

| 方式 | 对常离线设备 | 备注 |
|---|---|---|
| **SSH over tailnet** | ✅ 出站，失败重试 | 无需开端口；`git` / `rsync` 都走它 |
| 直连 TCP `100.x:port` | ✅ | 要过防火墙；端口对全 tailnet 可见 |
| `tailscale serve` | ✅ | `-bg` 重启后自动恢复；**Windows 需管理员终端** |
| `tailscale file cp`（Taildrop） | ❌ **两端都得在线**，且 Windows **只能发不能收** | 不适用 |
| Taildrive | ❌ 两端在线 | alpha，要改策略文件 |

**结论：只有「出站」方向的方式对频繁离线的设备省心。**

## 6. 实测（Syncthing 1.27.2，Linux amd64）

在隔离的临时目录里做的，`--home` 指到临时路径，测完清理，不碰系统配置。

| 指标 | 实测值 |
|---|---|
| 冷启动到 REST API 可用 | **1479 ms** |
| 进程数 | **2**（monitor + worker） |
| RSS 合计 | **57.8 MB**（monitor 19 + worker 38） |
| `POST /rest/system/shutdown` 后 | **零残留进程、端口释放** |
| 配置目录（首次生成） | **68 KB** |
| 二进制体积 | 13.6 MB（Windows zip）/ 8.7 MB（Linux deb） |

### 可用的驱动方式（零改造）

```bash
syncthing serve \
  --home=<插件状态目录>/syncthing \
  --no-browser --no-restart \
  --gui-address=127.0.0.1:<随机端口> \
  --gui-apikey=<随机 key>
```

然后用 REST API：

| 用途 | 端点 |
|---|---|
| 判断同步是否完成 | `GET /rest/db/completion` → `completion=100 && needItems=0` |
| 优雅退出 | `POST /rest/system/shutdown` |
| 暂停 / 恢复 | `POST /rest/system/pause` / `resume` |
| 触发扫描 | `POST /rest/db/scan?folder=<id>` |
| 设备 / 文件夹配置 | `/rest/config/...` |

**没有一步需要改 Syncthing 源码。**

## 7. 三个必须处理的问题

### ① 双进程模型

monitor（父）+ worker（子）。用 `POST /rest/system/shutdown` 能干净全退（实测零残留）。

**但别直接 kill 父进程** —— worker 可能活下来，monitor 也可能把它拉回来。**只用 shutdown API。**

### ② 同步端口默认绑 `[::]`

日志里是 `QUIC listener ([::]:22000)` —— **对所有网卡开放**，不只是 tailnet。GUI 可以用 `--gui-address=127.0.0.1:<port>` 锁死，但同步端口要在配置里改成只绑 tailnet 接口，否则局域网内任何设备都能尝试连它。

### ③ v1 与 v2 的 CLI 参数不兼容

v1.27 用 `--home`（双横线）但没有 `--log-level`；早期版本用单横线。**按需下载必须锁死版本号**，不能让它自动升级。

## 8. 设计方向（未实现）

### 三档状态，默认零开销

| 状态 | 磁盘 | 进程 | 内存 |
|---|---|---|---|
| **未安装**（默认） | 0 | 0 | 0 |
| **按需启停**（手动模式） | ~13 MB | 只在同步那几十秒 | 峰值 ~58 MB |
| **常驻**（用户主动开自动同步） | ~13 MB | 常驻 | ~58 MB |

### 下载的安全要求（如走「插件代下载」）

1. 只从官方 release URL 下，硬编码，不接受重定向
2. **SHA256 必须校验**，且把校验值显示在 UI 上
3. 下载前明确告知：是什么、多大、从哪来、装完会做什么

### sage-mem 侧需要补的两样

| 缺的 | 补法 |
|---|---|
| 人工裁决入口 | **冲突收件箱** —— 扫 `*.sync-conflict-*`，接进现有的冲突页签（2.0.0 已有冲突队列基础设施） |
| 手动推/拉闸门 | 通过 REST API 暂停 / 恢复 / 触发同步，做成 UI 按钮 |

### 记忆索引必须排除冲突副本

扫描记忆目录时跳过 `*.sync-conflict-*` —— 否则模型会把两套互相矛盾的记忆一起读进去。
