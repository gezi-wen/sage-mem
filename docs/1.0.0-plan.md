## 二、1.0.0 的定义已经改了（这是最重要的一条）

原计划：契约冻结 + 保证边界 + 评测报告 + 逐条复核。

**2026-10-15 的外部复审推翻了它的前提**：报告列 9 条问题（3 条 P1），六条最小反例在本机**全部复现**。
其中至少五条是**「承诺与事实对不上」**——代码在那些点上压根没被断言碰过，而契约、README、CHANGELOG
三处都写着承诺。当时 `npm test` 是 2508 条全绿。

所以 1.0.0 的核心不再是「我写下我保证什么」，而是：

> **每条「保证」都咬在一条会因它破损而变红的断言上。**

差别在于：前者是我说的话，后者是**能被机器推翻的话**。复审者的结论
「建议暂缓把本材料中的相关能力标为 1.0.0 保证」——那条线指的就是它。

## 三、要做的四件（按价值排）

### 1. 契约行 ↔ 断言名，做成机器可查的绑定

契约（`docs/1.0.0-contract.md`）里每个标「保证」的行，后面跟一个断言标识；再写一条元断言：

- 每个「保证」行**都有**标识；
- 标识指向的断言**真的存在**。

指不出来的行，只能降级成「尽力」或「未验证」。

同类的窄版本已经有了：`test/suite-registry-test.mjs` 盯「有没有写了不跑的套件」。
这一条盯「**有没有说了不验的承诺**」。**这是 1.0.0 的门槛项。**

⚠️ 它会把不少现在标着「保证」的行打回「尽力」。**那是产品口径，不是技术选择** —— 要问项目负责人。

### 2. 外部发现 → 断言，记成永久账

建 `docs/review-findings.md`：每条外部发现、处置、**对应的断言名**。
下一轮复审要能一眼看到「上轮说什么、怎么关的、现在由谁看着」，而不是重新猜。

2026-10-15 那轮的九条已在 `docs/1.0.0-review-response.md` 里逐条写了处置，
但**「对应断言名」这一列还没有** —— 补上它，并把机制固化下来。

### 3. 定性唯一 + 两份文档逐行一致

复审者抓到自相矛盾：边界表把「事件注册窗口」标成 best effort，契约正文别处又写成保证。
根因是**两份文档各自维护同一件事**。要么合并成一份，要么加一致性检查。

### 4. 桌面 / 网页 profile 上真跑一次探针

现状：**所有真实宿主实测都在 headless profile 上**；桌面版只做过 Inspect 查询
（读契约声明，**验不到「事件会不会到达」**）；网页版两条都没有。

而我关于「事件到达性」「写门是否真的被调到」的保证都建立在那上面。**必须问项目负责人**才能动实机。

## 四、明确不做

- **不再往里加功能。** 0.9.19 就是一边修一边加（写入门 + 冲突队列），结果两句承诺都不成立。
- **不上向量库、不做复杂热度排序、不做跨进程台账合并** —— 复审者也说这些不是缺陷，是边界。
- **不为了「功能完整」拉长 1.0.0**。下面三件明确留到 1.0.0 之后：
  - 难负例语料扩容（同名不同项目 / 相同实体不同时间 / 已失效内容 —— **现有语料完全没有构造**，
    属于题集扩容，不是调参能解决的）

  - 版本化基线历史（D19 重立基线后，0.9.16→0.9.19 那批改善不再被门看着）

## 六、必须带过去的三条经验（不带就会重犯）

这些是 2026-10-15 一天里用真金白银换来的，每一条都有事故。

### 1. 「测试全绿」不等于「事实对」

病根是**同一套假设**：测试、文档、实现从同一个理解里长出来，理解错了三者会**一起错、且错得一致**。
变异验证只能证明「改动会被抓到」，**证明不了「断言测的是对的东西」**——所有变异都在模型内部进行。

**可操作的判据**：每写一句对外的承诺，先指出它在**哪条断言**里；指不出来就标成「未验证」。
九条外部发现里至少五条是这么漏的。

### 2. 断言「不变量」，不要断言「机制」

本月**两次**因此让 Linux CI 变红、而本机全绿：

- `safeName` 用 `basename` 判目录成分 → Windows 上 `\` 是分隔符、Linux 上不是
- `watch-test` 断言「洪流哨兵把 ok 变 false」→ 洪流是 **Windows 专属**补丁，
  Linux 的 inotify 在目录被删时直接停发事件、**根本不洪流**（CI 实测 `{"ok":true,"fired":2}`）

写断言前问一句：**这条是两个平台/两种实现都必须满足的吗？** 不是就换成不变量。

### 3. 先测热点，再选方案；数字要能复现

- 性能：原以为热点是「排序」，实测是 **`open` 这个系统调用**（680 字节的文件打开一次 0.53 ms）。
  结论直接推翻了一个已被批准的方案（「只读文件头」只省 6%）。
- **性能脚本初版在同一进程换目录再 `import`**，而 `MEMORY_DIR` 是模块顶层读的 →
  第二三档扫的是已删目录，打出一行「规模越大反而越快」的假数字。现在每档独立子进程 +
  「扫到的文件数不符就整档报错」。
- **R01 一度假通过**：假宿主 `stat` 收路径、生产代码传 FsTarget，类型错误被当成了「守卫生效」。

**共同点**：绿/快/好看，与事实对，是三件事。

## 八、发布流程（已固化的纪律）

每版必须：**脱敏四查 → npm test 全绿（含 Linux CI）→ 行为变更写进 CHANGELOG →
四锚点核对 → 查 4（把包拉回来重扫）**。

两条踩出来的：

- **`git push` 到公开远端本身就是发布动作** —— 四查必须在 push **之前**跑。顺序反了只能重写历史，
  而 force-push 并不真正抹掉旧的 SHA。
- **「查 3」只覆盖本次要发的提交**。有多个未推提交时要**逐个**扫提交信息 ——
  历史里就漏过一处（老提交 `7462df9` 的信息里有服务器昵称，在 `origin/main` 里可达，
  项目负责人 2026-10-15 决定接受现状）。
