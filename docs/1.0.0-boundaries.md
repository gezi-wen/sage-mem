# 1.0.0 能力边界表（审查用）

> 版本 **0.9.19** · 整理于 2026-10-15
> 这份表只回答一个问题：**哪些能力你可以依赖，哪些只是我们尽量做到，哪些明确做不到。**
> 原始证据（探针输出、逐条实测）在 `docs/host-facts.md`；设计动机在 `docs/decisions.md`；
> 这份是给审查者的**结论表**，不重复证据过程。

---

## 一、这张表怎么用

### 四档定性（含义写死，不随上下文变化）

| 定性 | 含义 | 判据 | 你该怎么用它 |
|---|---|---|---|
| **保证** | 有断言支撑，而且**回归会红** | 断言位于登记进 `test/run.mjs` 的套件里 —— 每次 `npm test` 与 CI 都会跑 | 可以直接依赖 |
| **尽力** | 设计上如此，也有实测或文档依据，但**没有会红的回归断言**，或依赖未受控的外部条件（模型行为、宿主版本、平台） | 证据是探针实测 / 设计决定 / 代码审查 | 可以期待，但别写进你的架构假设 |
| **已知做不到** | 明确的能力边界 —— 不是待修的缺陷，是取舍 | 有代码注释或决定记录写明「为什么不做」 | 别指望它；理由见「依据」列 |
| **待验证** | 我们不知道 | 「怎么验」列给了具体手段 | 既不能当 yes，也不能当 no |

### 三条读表纪律

1. **「我们有测试」不等于「这是保证」。** 测试可能测的是别的东西。反面教材就在本仓库：
   `deliver-test.mjs`（75 条）与 `status-card-test.mjs`（51 条）在 0.9.17 / 0.9.18 两版里
   **没有登记进 `test/run.mjs`** —— `npm test` 从没跑过它们，而那两个版本的 CHANGELOG 都把
   条数列进了表格（0.9.19 已更正并补登记）。所以本表每一行都指向**具体套件的具体组**，
   不写「有测试覆盖」了事。
2. **「保证」的范围是那一条断言，不是它旁边那句话。** 例：写入门有 64 条判定断言 + 18 条接线
   断言，但它们都跑在 mock 上 —— 所以「判定逻辑」是保证，「真实宿主里事件会到」不是。
3. **`inconclusive` / 「没触发」不许读成 pass。** 探针的检查器本身用断言钉住了这一点（见 A4）。

### 本版口径（可复算）

- `npm test` 实测：**2408 passed, 0 failed**，37 个套件全部 `exit 0`。
- 所有真实宿主实测都在 **Windows + Node 24.x** 上做；CI 跑的是 **ubuntu-latest + Node 24.x**，
  同一批断言跑两遍（第二遍 `TZ=UTC`）。
- 定性统计：**保证 13 · 尽力 7 · 已知做不到 9 · 待验证 5**（共 34 行）。

  （`hasFs` / `hasStat` 均为真），代码里就是这条路线。它现在的定性是 A7 那行的「尽力」。
- **本表不含 UI 观感、文案与交互验收**：`test/client-render-test.mjs` 覆盖的是渲染形状与状态，
  不是「好不好用」。

## 三、如果要升到 1.0.1，最该先补哪三条

排序口径 = **风险 × 可验证性**（两者各 1–5 分，分数写在下面，便于你不同意权重时自己重排）。

| 顺位 | 补什么 | 风险 | 可验证性 | 乘积 |
|---|---|---|---|---|
| 1 | 套件登记守卫 | 4 | 5 | 20 |
| 2 | 写入门真实到达性的守护 | 5 | 3 | 15 |
| 3 | web / desktop profile 的探针覆盖 | 4 | 3 | 12 |

**1. 套件登记守卫（`test/run.mjs` 自检）—— 风险 4 × 可验证性 5**
- 为什么：**假绿已经真实发生过**（两个版本、126 条断言、两版 CHANGELOG 都把它们列进了表格）。
  现在虽然 37/37 对得上，但**没有任何机制阻止下一个人再忘一次**。
- 怎么补：`test/run.mjs` 自己在跑之前比对 `SUITES` 与 `test/*.mjs`，有未登记的就失败。
  一条断言、几行代码，永久生效。
- 为什么排第一：它是唯一一条**几乎零成本、且能把已发生过的事故类别彻底关掉**的补法。

**2. 写入门真实到达性的守护 —— 风险 5 × 可验证性 3**
- 为什么风险最高：`CHANGELOG.md` 0.9.19 把它写在**「行为变更」**（给升级者看的承诺）里；
  `test/write-gate-test.mjs`（64）与 `write-gate-wiring-test.mjs`（18）全绿；`npm test` 2408 条全绿 ——
  三重信号都在说「这是保证」。但它**在真实宿主里能否收到事件**只有探针实测，没有任何回归断言：
  而且按项目**自己的 D5 规范**（可选服务用 `ctx.inject` 挂子 fiber）去「顺手统一」一下注册方式，
  就会**静默失效** —— 编译得过、`npm test` 照样全绿，只是永远不触发（A7）。
- 怎么补：把「注册必须发生在**不声明 `inject`** 的早期上下文」变成一条会红的断言
  （最直接的是对 `lib/index.js` 做源码级断言：不得出现 `static inject` / `export const inject`，
  与 `observe-test.mjs` 已有的源码级断言同一手法）；真实宿主那一半进**发布清单**并留基线，
  因为 CI 的容器里没有 DSH 宿主。
- 为什么不是第一：风险最高，但在 CI 里只能验到「写法没变」，验不到「宿主会给」——
  可验证性只有中等。

**3. web / desktop profile 的探针覆盖 —— 风险 4 × 可验证性 3**
- 为什么：目前**所有**真实宿主结论都来自 headless。而插件是按 profile 挂载的，
  `dsh.bundle` 对任何 profile 都生效 —— 也就是说这两条入口都在支持范围内，
  却一条都没实测过；桌面版更彻底：它被宿主独占（CLI 加不了 `--patch`），
  连「服务拿不拿得到」都无从验证（D5 / D6）。
- 怎么补：web 侧成本很低（一次性 patch + 跑完关掉）；desktop 侧需要一个 GUI 加载通道，
  或把插件临时装进一个试验 profile、测完摘掉。两者都要写进发布清单，因为它们进不了 CI。
- 为什么排第三：风险不低，但验证要人工启宿主、且结论只覆盖「跑的那一次」，
  可验证性中等。
