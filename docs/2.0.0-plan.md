## 零、结论（先看这 10 条）

1. **2.0.0 = 矛盾检测。** 给记忆加 `valid_at` / `invalid_at`（外加可选 `superseded_by`），把冲突队列从「只落记录」变成「能读、能裁、能抑制注入」。
2. **注入侧改动比想象中小。** `deliver.js` 两条规则早就写好了 —— 未裁决冲突 → `unresolved/conflict_pending`（`lib/memory/deliver.js:175-178`）、失效 → `unresolved/expired_source`（`lib/memory/deliver.js:172-174`）。2.0.0 只需在 `lib/recall/compose.js:67-70` 把两个硬编码空集换成真数据；**`deliver.js` 计划一行不改**，这是本设计最重要的一条。
3. **只对「矛盾型」冲突抑制。** 现有三种冲突都是**写失败**型（`stale_version` / `external_change` / `unresolved_merge`，`lib/memory/conflicts.js:37`），盘上那份仍是现行内容；一并抑制等于把「这次没写进去」误报成「记忆失效」。新增 `contradiction`，只它触发抑制。
4. **冲突记录只增不改**：字段追加在尾部、`v` 保持 1。1.9.x 读端仍能读（只要求 `id` 与非空 `status`，`lib/memory/conflicts.js:353-366`）。
5. **「失效」写在记忆 frontmatter 里**，不删文件、不移动、不进 `archive/`（「记忆目录自包含」是立身之本，`docs/1.0.0-contract.md:43`）。代价：裁决要写记忆文件，必须走版本守卫（D4，`docs/decisions.md:54-75`）。
6. **裁决入口 = 新「冲突」页签 + 头部徽标 + `conflict.*` remote。** 三个既有 Gateway 类仍留在 `lib/index.js`（`sourceLocation` 硬编码，`lib/typert.host.js:528`），新 Gateway 照 `StarmapGateway` 写法挂（`lib/index.js:58-59`）。
7. **抑制绝不静默。** 状态卡加一句「有 N 条矛盾待裁决」，面板常显徽标 —— D27 拒绝「先接抑制」的理由（`docs/decisions.md:632`）要在 2.0.0 正面解决。
8. **「较新说法优先」用边失效实现，不做时间加权排序。** 旧说法标了 `invalid_at` 就不进注入；不引入隐式规则（排序细节本来不在契约里，`docs/1.0.0-contract.md:81`）。
9. **分三片发**：alpha.1 数据模型 + 只读审计 → alpha.2 remote + 面板只读 → 2.0.0 完整裁决 + 注入生效。前两片不改注入行为，每片可单独回滚。
10. **8 个问题需要拍板**（§11.2），其中 3 个决定数据模型形状，越早定越便宜。

## 一、一句话目标与「为什么是 2.0.0」

### 1.1 目标

**让「这条记忆已经不作数了」成为文件里可核对的事实，并让注入链真的按它办事 —— 不靠删文件，不靠模型自觉。** 配套三件事：人工裁决（面板 + remote）、抑制生效（`conflict_pending`）、被抑制时一定看得见（状态卡 + 徽标）。

### 1.2 会变的公开面

| 公开面 | 1.9.2 现状 | 2.0.0 变成 | 证据 |
|---|---|---|---|
| 注入内容 | 有未裁决冲突的记忆照常注入正文 | 矛盾型两方都不进正文；带 `invalid_at` 的也不进 | `README.zh.md:296`、`lib/recall/compose.js:69` |
| frontmatter | 认 `description` / `type` / `tags` / `updated` / `aliases` / `baseline` | 再认 `valid_at` / `invalid_at` / `superseded_by` | `lib/memory/frontmatter.js:38-75`、`docs/1.0.0-contract.md:45` |
| 冲突队列 | 只写不读 | 可列、可读、可裁决、可撤销 | `lib/memory/conflicts.js:9-12` |
| 面板 | 无冲突入口 | 多一个页签 + 头部徽标 | `client/70-memory-panel.js:792-805` |
| remote 面 | 33 条 invocation | 新增 `conflict.*` 若干条 | `test/structure-test.mjs:107-122` |
| 离线评测基线 | 语料指纹 `ad241c11a360` | 加标记后指纹变化，**必须重立基线** | `docs/retrieval-diagnostics.md:8`、`scripts/eval-retrieval.mjs:926-929` |

### 1.3 为什么按 MAJOR 走

「新增能力」本可走 MINOR（`README.zh.md:440-447`）。四条理由：

1. **翻转一条已写进 README 的行为承诺。** `README.zh.md:296` 现在明说「注入侧目前不读这个队列」并给出手工处理方式；2.0.0 之后这句话必须反过来。
2. **默认行为变了。** 升级后同一问题的答案依据可能**变少**：被标失效的那条不再出现。
3. **往用户的记忆文件里写新字段。** 1.9.x 读端静默忽略这些键（`lib/memory/frontmatter.js:46-52`），降级不报错，但「失效标记在旧版本不生效」是单向阀。
4. **评测口径要重立。** 加标记改语料指纹，`--baseline` 判「不可比」（`scripts/eval-retrieval.mjs:1326-1343`）；按 D12 / D19 先例，重立基线要单独写进 CHANGELOG（`docs/decisions.md:347-356`、`:79-116`）。

### 1.4 迁移与弃用

- **旧记忆零迁移**：没写新字段 = 「有效、时间未知」，与 1.9.2 逐字相同（§4.1 R1）。不写迁移脚本、不改状态目录布局、不加新环境变量（除非 §11.2 Q8 拍板）。
- **读兼容双向**：1.9.x 能读 2.0.0 的记录（字段只增不改）；2.0.0 能读所有 1.9.x 记录（`v` 不校验，`lib/memory/conflicts.js:353-366`）。
- **弃用项**：暂无字段/接口被删。`expectedVersion: 'unknown'` 继续保留 —— 它诚实表示「没拿到版本号」（`lib/autodream/tools.js:626`）。
- **不做的迁移**：不批量补 `valid_at`。补了就是编时间（同 `lib/memory/conflicts.js:173-176` 的「认不出就是空串，不编」）。

### 1.5 更名说明

这个版本在文档里用过好几个号：README 的「写入安全」一节一度写作 **1.10.0**（1.9.2 已把该处引用改成 2.0.0，更名本身记录在 `docs/decisions.md:632`）；`test/eval/README.md` 里还留着更早的「属于 1.9.0 的矛盾检测」；`CHANGELOG.md` 的 1.7.2 章节也写着当时的排期。项目负责人已定名为 **2.0.0**。

**处理口径**：只改「面向未来」的引用（README 现行说法、路线图、decisions 里对未来版本的指路 —— 1.9.2 已改完）；**不重写已发布版本的历史章节**：CHANGELOG 的 1.7.x/1.8.x 记录与旧评测报告里的排期是当时的真实上下文，改了才是伪造历史。

## 三、术语表

一个词一个定义；右列是容易混的那个词。

| 词 | 定义 | 容易混的是 |
|---|---|---|
| **记忆** | `memory/` 下一个 `.md`（frontmatter + 正文），一条记忆一个文件 | 不是「一段正文」；段落只是检索粒度 |
| **冲突** | 一次没落地的写入或一次待判定分歧，落成 `<状态根>/conflicts/<id>.json` | 不是正文 diff；我们不比差异，只记录两份正文 |
| **矛盾** | 两条记忆对同一件事给出互相排斥的说法 | 矛盾是冲突的一种（`kind: contradiction`） |
| **裁决** | 人决定哪条说法算数，并落成状态变化 | ≠ 自动合并；≠ 删除记录 |
| **失效（invalid）** | 说法不再作为现行口径，文件里表现为 `invalid_at` 有值 | ≠ 归档 ≠ 删除；文件仍在、仍可读 |
| **有效（valid）** | 说法当前可作依据；缺省即有效 | ≠ 被注入；相关性是另一道门 |
| **取代（supersede）** | 新说法让旧说法不再成立；写旧条目 `invalid_at` + 可选 `superseded_by` | 不是改名/移走旧文件 |
| **抑制（suppress）** | 本轮注入不带正文；来源是失效或未裁决矛盾 | ≠ 删除；模型仍可用工具主动读 |
| **待裁决** | 冲突记录 `status === 'open'` | 徽标数的就是它 |
| **只标不删** | 失效只写 frontmatter，绝不 unlink / rename / 移入归档 | 与「归档」是两种动作，文案不许混用 |

## 四、数据模型

### 4.1 frontmatter：`valid_at` / `invalid_at` / `superseded_by`

三者都**可选**、都是**字符串**、写在顶层（与 `updated` 同级）：

```yaml
valid_at: 2026-10-20T09:00:00+08:00      # 说法从什么时候开始成立（事件时间）
invalid_at: 2026-10-24T18:30:00+08:00    # 从什么时候起不再作数（事件时间）
superseded_by: project_beta.md           # 可选：现行口径在哪条记忆里
```

| 字段 | 语义 | 格式 | 缺省 | 谁写 |
|---|---|---|---|---|
| `valid_at` | 说法开始成立的时间（世界时间，不是文件修改时间） | ISO 8601 带偏移：`YYYY-MM-DDTHH:MM(:SS)?(Z|±HH:MM)` | 缺失 = 时间未知 | 模型整理、人工编辑 |
| `invalid_at` | 从这刻起不再作为现行口径 | 同上 | 缺失 = 仍有效 | 裁决入口（§7.3）、模型整理、人工编辑 |
| `superseded_by` | 指向现行口径的文件名（线索，不是外键） | 文件名，不是路径 | 缺失 = 无指针 | 裁决入口、模型整理 |

**判定规则（实现逐条照做）：**

- **R1 缺失即老行为。** 三字段全缺 → 「有效、时间未知」，与 1.9.2 逐字相同；这是零迁移的全部依据。
- **R2 认不出就不猜。** 过格式正则且 `Date.parse` 有限才认，否则按「未标注」处理（同 `lib/memory/conflicts.js:173-176` 对 `at` 的口径）；审计单列**提示**、不进 `problems`（`problems` 是唯一健康数字，不能变噪音 —— issue #8 的教训，`CHANGELOG.md:58`）。
- **R3 失效判定看时钟，但时钟必须显式传入。** 可解析且 `invalid_at <= nowMs` → 失效；未来时间 → 暂不失效（审计提示）。纯函数收 `nowMs`（先例 `lib/memory/retrieval.js:148-154` 的 `ageDays`；注入链已有 `nowMs`，`lib/recall/injector.js:87`）。⚠️ 别在模块里读 `Date.now()`：夹具与 `TZ=UTC` 的 CI 会不可复现。
- **R4 与 `updated` 互不推导。** `updated` 仍是「文件何时被改过」，只喂新鲜度；`valid_at` 是「事实何时成立」。两者可以差很远（补写旧事实：`updated` 今天、`valid_at` 去年）。
- **R5 只加键，不动别的字节。** 只插入/替换这几行，保留键顺序、缩进、行尾（CRLF 必须原样保留 —— `lib/memory/frontmatter.js:39-43` 记的正是 CRLF 让整条记忆检索不到那次）；写法复用归档留痕先例：先剥旧行再插（`lib/memory/scan.js:93-107`）。
- **R6 `superseded_by` 不做一致性校验。** 目标可能被归档/改名；只校验文件名合法，审计给提示，检索不依赖它。

解析落点：扩 `parseFrontmatter`（`lib/memory/frontmatter.js:38-75`）返回三字段，再让 `fullScanMemoryDir` 带进 `files` 记录（现带 `description` / `aliases` / `baseline` / `baselinePriority` / `updated` / `mtimeMs`，`lib/memory/scan.js:446-459`）。⚠️ 别另写「只解析这三个字段」的小解析器 —— D22 的教训是同一判据多一份实现就会漂（`docs/decisions.md:513-538`）。

### 4.2 冲突记录：扩哪些字段、`kind` 加什么

**决定：字段只增不改，`v` 保持 1。** 解析器只校验 `id` 与 `status`（`lib/memory/conflicts.js:353-366`），升 `v` 没有读者会看，只会多一份迁移。

追加在末尾的可选字段：

| 字段 | 语义 | 缺省 |
|---|---|---|
| `otherFile` | `contradiction` 的另一方；本记录 `file` 是**被提议标失效**的一方 | `''` |
| `decision` | `invalidate` / `dismiss` / `keep_both` | `''` |
| `decidedAt` | 裁决时间（ISO 8601，由调用方给，不读时钟 —— 同 `buildConflict` 的 `at`） | `''` |
| `appliedVersion` | 写 frontmatter 时宿主返回的版本（收据） | `''` |

`kind` 新增 **`contradiction`**，与现有三种划清：

| kind | 来源 | 抑制注入 |
|---|---|---|
| `stale_version` | 写时被版本守卫拒绝（`lib/autodream/tools.js:716`） | 否 |
| `external_change` | 没读过内容、拒绝盲写（`lib/autodream/tools.js:706`） | 否 |
| `unresolved_merge` | 人工合并到一半（预留，当前无写入者） | 否 |
| `contradiction` | 两条记忆说法互斥（§5.2） | **是**（两方都不进正文） |

⚠️ 必须同笔改的冻结断言：`CONFLICT_KINDS` 是冻结列表且逐字钉住（`lib/memory/conflicts.js:37`、`test/conflicts-test.mjs:98-101`）；同时记一条新决定（D29 起）。

**id 与去重：**

- id 规则不动：`[紧凑时间戳-]8 位内容指纹`（`lib/memory/conflicts.js:229-231`）。
- 去重判据不动：落盘前查未裁决队列、逐字段相同就跳过（`lib/autodream/tools.js:653-670`），但**把 `otherFile` 加进比较列表** —— 否则「A 对 B」与「A 对 C」会被当成同一件事。
- 矛盾记录的两份正文映射到既有字段：`incoming` = 新说法/拟保留方正文，`onDisk` = 旧说法/拟标失效方正文。⚠️ **不要**加新正文字段：那会重写 256 KB 预算与 `fitBodies` 削法（`lib/memory/conflicts.js:267-292`），收益只是名字好听；语义写进本条决定与面板文案。
- 256 KB 与单字段 48 KB 继续生效（`lib/memory/conflicts.js:51`、`:61-68`）；两份都超限时仍只削大的那份并置 `truncated: true`（`:282-290`）。

### 4.3 「只标不删」落在哪：frontmatter 还是旁路索引

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 写记忆 frontmatter**（推荐） | 记忆目录自包含；可 `git diff`；状态根丢了标记也在；与 `archived_at` 做法一致（`lib/memory/scan.js:93-107`）；一个事实一个出处 | 裁决要写记忆文件，必须走版本守卫与逐次沙箱策略；写失败要留记录；长 frontmatter 要小心 |
| B. 旁路索引（`<状态根>/invalid.json`） | 不碰用户文件；写入快 | 状态根一删标记全没、失效记忆悄悄复活；记忆目录不自包含；同一事实两个出处（违反 D22 精神）；换机器带记忆目录会丢标记 |

**推荐 A。** 代价照收：写路径必须满足 §5.5 的五条；写失败一律返回错误并留待处理记录。

**「只标不删」的具体含义（验收按这五条查）：** ① 文件仍在原目录、文件名不变；② 正文一个字节不变（除 frontmatter 新增/修改那一行）；③ 不写 `archive/`、不写 `.archiving-*` 中转名（`lib/autodream/audit.js:34-43`）；④ 不改 `updated`（它不是失效时间）；⑤ 撤销时只删我们写的那一行，其他字节不动。

### 4.4 数据模型不变量

- 有效性只由记忆自己的 frontmatter 决定；冲突记录是**审计与待办**，不是事实来源。两者不一致时：注入看 frontmatter，面板看记录。
- 任何字段缺失都必须是「老行为」，不是报错、也不是猜测。
- 状态目录的冲突记录只增不迁移；删除只发生在用户明确点「删除记录」时。
- 所有新解析/判定函数必须是纯函数（收 `nowMs`、不读盘、不读时钟），否则测不了。

| 写者 | 路径 | 写什么 | 守卫 |
|---|---|---|---|
| **人**（面板裁决） | 新 remote `conflict.invalidate` | `invalid_at`（+ 可选 `superseded_by`）、记录状态 | 宿主写 + `expected` 版本（D4） |
| **模型**（自动做梦） | 既有 `write_memory` 写整份内容（`lib/autodream/tools.js:688-720`） | 模型自己在 frontmatter 里写新字段 | 已带「读到内容那一刻」的版本（`:698-707`） |
| **人**（手工编辑） | 编辑器 | 任意 | 不经过插件（写门只对工具写入给版本，`README.zh.md:292`） |
| **写门 / 宿主工具** | 宿主 `write` / `edit` | —— | 只给版本、**不落冲突记录**（`README.zh.md:292`） |

明确不许：插件不替模型决定哪条失效；面板不把「较新」自动当「有效」。

### 5.2 矛盾是怎么被发现的（本版唯一「新检测」）

不做常驻扫描。检测只发生在**自动做梦**这条已有路径：

1. 整理时模型读到两条互斥说法；
2. 模型在**整理声明**里列出这对（新增内部字段，例 `contradictions: [{old, new, note}]`；整理声明是内部产物，不进契约）；
3. 引擎在 **apply 之前**落成 `kind: contradiction` 记录（两方文件 + 两份正文 + `note`）；
4. 裁决前两方都不进正文（§6.3），裁决后败方写 `invalid_at`。

**驳回「新增模型工具 `mark_conflict`」**：工具面是契约 3.1 / 3.2 的保证（`docs/1.0.0-contract.md:72-73`），为插件自己能记录的事再加公开工具，会永久多一份 schema 与文档；而且给模型一个随时可调的「标失效」入口，等于给自动裁决留暗路。**代价**：检测延迟到下次整理、且只能整理时发现 —— 接受，因为 D7 承诺不做常驻服务。

**驳回「读取时惰性检测」**：词法层没有「两句互斥」的判据，硬做会把误报写进记忆。**明确做不到。**

### 5.3 与写入门、版本守卫、autodream 的关系

| 既有机制 | 2.0.0 怎么用 | 不做的事 |
|---|---|---|
| 写门（`fs/write-intent`） | 不动。它只覆盖工具发起的写入，插件自己写仍要传 `expected`（契约 6.8，`docs/1.0.0-contract.md:128`） | 不扩写门去拦失效标记 |
| 版本守卫（D4） | 写 frontmatter 前必须拿到版本；拿不到就不写，返回 `stale_version` / `unsupported` | 不拿「当前版本」冒充「读到的版本」（R01 教训，`lib/autodream/tools.js:463-526`） |
| 逐次沙箱策略 | 沿用 autodream 的收窄策略（`lib/autodream/tools.js:544-576`） | `read-only` 宿主不绕过围栏（`CHANGELOG.md:56`） |
| autodream `write_memory` | 模型写整份内容时可带新字段；引擎不二次改写 | 不自动补 `valid_at`、不做语义复核 |
| 冲突队列 | 三类写失败照旧（`lib/autodream/tools.js:615-640`），新增矛盾型 | 不把写失败冲突升级成「失效」 |

### 5.4 写失败与冲突记录

- **版本过期 / 内容未读过**：返回错误 + 落记录（沿用 `lib/autodream/tools.js:615-640`），不让调用方以为写成功。
- **沙箱拒绝**：返回 `write_denied`，面板给可诊断出路（照 `lib/autodream/tools.js:595-603` 的口径）。
- **IO 失败**：返回 `io_error`，记录仍 `open`，可重试。
- **部分成功不存在**：一次裁决只写一个文件的 frontmatter；要么落、要么不落。

### 5.5 写路径的硬性要求

1. **幂等**：同一条记录连点两次「标失效」，第二次不重写、不报错（同 `resolveConflict` 同状态幂等，`lib/memory/conflicts.js:484`）。
2. **不半份**：原子写（宿主 `writeText` 或 `writeFileAtomic`，见 `lib/memory/conflicts.js:25`），失败不留改了一半的文件。
3. **不动别的字节**：保留顺序/缩进/CRLF（§4.1 R5）。
4. **不改 `updated`**：失效不是「文件被改过」，改了会让新鲜度提示说谎。
5. **给收据**：成功返回 `{ok, file, invalidAt, version}`；失败返回 `{ok:false, code}`，永不在成功时缺字段。

## 六、检索与注入语义

### 6.1 失效记忆默认不参与注入，但仍可被工具读到

- **注入**：带已到点 `invalid_at` 的记忆 → 不进正文。
- **工具**：`search_memory` / `read_memory` 照旧能搜到/读到，结果**追加**可选字段 `invalidAt` / `supersededBy`。理由：模型有时就在问历史，旧口径是证据不是噪音；契约 2.x / 3.x 都没承诺「检索结果只含有效记忆」，加字段是追加。⚠️ 要拍板（§11.2 Q3）。
- **面板 / 星图**：照旧全读，卡片打「已失效」徽标。

### 6.2 两条既有规则接上真实集合（`deliver.js` 一行不改）

链路是 `scan` → `selectRecall` → `buildCandidates` → `composeDelivery`（`lib/recall/injector.js:71-97`）。后者的两个集合现在是硬编码空集：

```js
conflicts: new Set(),   // lib/recall/compose.js:69
expired: new Set(),     // lib/recall/compose.js:70
```

2.0.0 换成真数据（一个纯函数：从 `files` 取失效名单，从冲突队列取未裁决矛盾的两方），其余不动。

| 记忆状态 | 传进 `decideDelivery` 的集合 | kind / reason | 进正文? |
|---|---|---|---|
| 有效、相关 | —— | `snippet` / `evidence_missing` 等 | 是 |
| `invalid_at` 已到点 | `expired` | `unresolved` / `expired_source` | 否 |
| 有未裁决矛盾 | `conflicts`（两方都放） | `unresolved` / `conflict_pending` | 否 |
| 两者都有 | 优先 `expired`（规则 3 先于 4） | `expired_source` | 否 |

最后一行已有断言：`test/deliver-test.mjs:90-92`（过期先于冲突）。**这就是 `deliver.js` 不用改的原因**：规则顺序、理由枚举、`totals` 都在原处（`lib/memory/deliver.js:98-107`、`:148`）。

⚠️ 代价：失效/冲突记忆仍占检索候选位（到显示层才判 `unresolved`），极端情况下少一个有效候选。本版接受，换来 `expired_source` 的可解释性与规则复用；若真机实测有影响，再考虑在 `selectRecall` 前置过滤 —— 那时必须同时把「被剔除几条」搬进状态卡，否则就从「能解释」退回「静默」。

### 6.3 只对「矛盾型」抑制

1.9.2 里三种冲突都是「想写、没写成」：`stale_version` 时**盘上那份才是现行的**（`lib/autodream/tools.js:716`）；`external_change` 是我们没读过内容（`:706`）；`unresolved_merge` 是合并到一半。把它们也塞进 `conflicts` 集合，等于把「这次没写进去」误报成「这条记忆不可信」—— D27 担心的「记忆消失」换了个入口重演（`docs/decisions.md:632`）。所以**只有 `kind: contradiction` 的 open 记录进入 `conflicts` 集合**。

**反向对照（必须写进测试）**：存在一条 `stale_version` 的 open 记录时，对应记忆**照常注入**。

### 6.4 抑制绝不静默

D27 拒绝先上抑制的理由是「用户唯一解除方式是手工编辑 JSON」。2.0.0 必须让它在界面可见：

1. **状态卡多一句**（上限 512 字节，`lib/memory/status.js:15`）：例 `sage-mem：另有 2 条矛盾待裁决，相关记忆本轮未注入正文。`；
2. **强制发卡**：即使 `parts.length === 0`，只要 `pendingConflicts > 0` 就必须发卡（出口在 `lib/recall/injector.js:160-163`，要保证「全被抑制」一定走到卡）；
3. **头部常显徽标**：与体检徽标同一套（`client/70-memory-panel.js:814-819`）。

⚠️ 卡按内容签名去重（`lib/recall/compose.js:146-158`），句子里必须带**具体条数**，否则签名不变、第二封发不出去。

### 6.5 「较新说法优先」= 边失效，不是时间加权排序

- 新说法有效、旧说法 `invalid_at` → 旧的直接不进注入，**不需要排序改动**。
- 不做「分数 + 时间加成」：那是隐式规则，会拿新写的无关记忆压掉旧的相关记忆，错的方向正好是误注入（排序细节不承诺，`docs/1.0.0-contract.md:81`）。
- 两条都没标时不推断 —— 检索照旧按分数走（这也是「相同实体不同时间」难负例 4/4 旧版压新版的成因，`test/eval/README.md:200`）；标记补上后才变化。

### 6.6 性能

每步 assemble 多一次「读冲突队列」（`listConflicts` 读目录 + N 个 JSON）。先不加缓存，用 `scripts/perf-chain.mjs` 量：**100 条 open 记录时单步增量 p95 < 2 ms**（与现状 p50 1.170 ms / p95 1.808 ms 同量级，`docs/retrieval-diagnostics.md:28`）；超阈值再上进程内小缓存（按目录名集合 + mtime 失效，不落盘，同 D2 口径）。⚠️ 别把冲突队列塞进记忆目录的扫描缓存：两个目录、两套失效判据。

### 6.7 对评测指标的预期

| 指标 | 1.9.2 现状 | 2.0.0 目标（**测量，不是承诺**） | 怎么量 |
|---|---|---|---|

## 七、裁决入口

### 7.1 面板落点

**推荐：新页签「冲突」，排在「体检」之后**（页签列表在 `client/70-memory-panel.js:792-805`），加**头部常显徽标**（照体检徽标写法，`:814-819`）。

理由：裁决是**多动作、要逐条看两份正文**的流程，不是一次性诊断工具 —— 与 D25 把「注入调试」塞进抽屉的前提（一年用不了几次）相反（`docs/decisions.md:587-591`）；空态零负担；徽标解决发现性。⚠️ 会改「五个页签」快照断言（`test/client-render-test.mjs:1605-1608`），属有意更改（§9.2）。备选见 §11.2 Q4。

### 7.2 每条冲突展示什么

| 区块 | 内容 | 备注 |
|---|---|---|
| 头部 | 记录时间、`kind` 徽标、状态（待裁决/已裁决） | 时间用记录里的 `at`，不读时钟 |
| 涉及文件 | `file` 与 `otherFile`，可点击查看该记忆 | 文件名钳制长度，防超长名撑破布局 |
| 两份正文 | 默认折叠；展开对照，各显示前 2 KB | ⚠️ 记录可能被截断（`truncated: true`，`lib/memory/conflicts.js:301-303`），要显示「已截断」 |
| 说明 | 记录里的 `note` | 不重写 |
| 动作 | 见 §7.3 | 危险动作两段式确认 |

### 7.3 动作表（幂等 / 可逆 / 写不写盘）

| 动作 | 对记录 | 对记忆文件 | 可逆 | 二次确认 |
|---|---|---|---|---|
| **标此条失效**（`invalidate`，传 `file`） | `resolved` + `decision: invalidate` + `decidedAt` + `appliedVersion` | 加 `invalid_at`（= 裁决时刻）+ 可选 `superseded_by` | **是**：撤销删掉这两行 | 是（写文件、影响注入） |
| **标记已裁决**（`dismiss`） | `dismissed` + `decision: dismiss` | 不写 | 是（`resolved ↔ dismissed` 允许，`lib/memory/conflicts.js:78-82`） | 否 |
| **撤销失效**（`undo`） | 清 `decision`/改 `dismissed` | 删掉 `invalid_at` / `superseded_by` | 是（再标一次即可） | 是（写文件） |
| **删除记录**（`remove`） | unlink 记录 | 不写 | **否**（只剩日志/备份） | 是（两段式，照「彻底删除」先例：`client/50-shared-ui.js:354-356`） |
| **手工合并** | 不改 | 不写；只打开目录/文件 | 是 | 否 |
| **重放待写内容** | —— | —— | —— | **不提供**（§7.4） |

- 同状态重复操作**不重写文件**（`lib/memory/conflicts.js:484`）。
- 记录**永不许回到 `open`**（`lib/memory/conflicts.js:78-82`）—— 「撤销」是变 `dismissed` + 清标记，不是复活成待裁决；要重新讨论就新建一条（现状设计，不改）。
- 写失败时**记录保持 `open`**，面板显示错误与出路；不允许「记录已裁决、文件没改」的半态。

### 7.4 不自动应用待写内容（明确建议）

`stale_version` 记录里存着「想写的那一版正文」。**不提供一键写回**：那份内容的依据是当时的盘上版本，现在早已变了；应用它等于绕过版本守卫的意义（本次冲突就是这么来的）。用户真要，手工合并更安全。结论：处理完**只解除抑制**，不自动应用任何正文；写进 README 与面板文案。

| 缺什么 | 表现 | 先例 |
|---|---|---|
| 没有 `fs` 服务 | 面板可看、动作禁用，返回 `unsupported`，提示手工编辑 | `lib/autodream/tools.js:688-694` |
| 没有 locale 服务 | 界面回中文（`ZH` 兜底） | `client/55-i18n-memory.js:384-390` |

| 冲突目录不存在 | 空列表，不是错误 | `lib/memory/conflicts.js:420-428` |
| 单条记录坏掉 | 进 `broken`，其余照列 | `lib/memory/conflicts.js:408-417` |

### 7.6 remote API 契约

新增 service `conflict`（第四个 Gateway，类留在 `lib/index.js`）。入参/返回全部 JSON 可序列化。

| 方法 | 入参 | 返回 | 错误码 |
|---|---|---|---|
| `list` | —— | `{ok, items, broken, ignored, counts:{open,total}}` | `io_error` |
| `read` | `{id}` | `{ok, record, warnings}` | `invalid` / `missing` / `malformed` / `io_error` |
| `invalidate` | `{id, file, note?}` | `{ok, record, wrote:{file, invalidAt, version}}` | `invalid` / `missing` / `malformed` / `invalid_transition` / `stale_version` / `write_denied` / `unsupported` / `io_error` |
| `dismiss` | `{id, note?}` | `{ok, record}` | 同上去掉写入类 |
| `remove` | `{id}` | `{ok}` | `invalid` / `missing` / `io_error` |

⚠️ **实现时把 `remove` 改名成 `removeRecord`**（invocation id 同步为 `sage-mem#conflict/removeRecord`）：客户端 `RemoteNamespaceService` 会把与 Cordis Service 原型同名的方法判成「conflicts with its namespace service」，`remove` 是其中之一 —— 真机上表现为**整个 client 插件 activate 失败**（六页签全不见）。理由与守卫见 `docs/decisions.md` D29 与 `lib/index.js` 里 `ConflictGateway.removeRecord` 的注释；`test/structure-test.mjs` 有保留名断言。
| `undo` | `{id}` | `{ok, record, cleared:{file}}` | 同上 |

约束：`id` 必须过 `normalizeConflictId`（`lib/memory/conflicts.js:92-123`）；`file` 必须是记录里出现过的 `file` 或 `otherFile` —— 防「借裁决入口写任意记忆文件」；所有失败**返回对象、绝不抛**（同 `lib/memory/conflicts.js:369`）；`invalidate` 幂等，并且**先写文件、后改记录**（反过来会出现「记录说已裁决、文件没改」）。

## 十、迁移、回滚与兼容

### 10.1 旧记忆（没有新字段）

全部按「有效、时间未知」处理 —— 与 1.9.2 的唯一区别是「多解析了三个键」，不存在时为空串，`selectRecall` / `deliver` 行为完全不变（R1）。验收就是 `recall-golden` 11/11 与 `inject-test` 旧断言全绿。**不做批量回填**（回填就是编时间）。

### 10.2 版本回退到 1.9.x 会不会坏

| 回退后 | 会发生什么 | 判据 |
|---|---|---|
| 记忆里的 `invalid_at` | 被忽略 → 失效记忆**重新注入** | `lib/memory/frontmatter.js:46-52` 只抓已知键 |
| 冲突记录 | 1.9.x 只写不读，文件留着无害 | `lib/recall/compose.js:69` 仍是空集 |
| `contradiction` 记录 | 同上；解析器不管 `kind`（`lib/memory/conflicts.js:351-366`） | 不会判坏 |
| 面板 | 没有「冲突」页签，记录看不见但不影响行为 | —— |
| 数据损坏 | **不会**：回退不写任何文件 | —— |

**结论**：回退是「功能消失」，不是「数据损坏」。这句原样写进升级提示。

### 10.3 冲突记录格式变化怎么办

1.9.x 写下的记录照读，新字段缺省为空（§4.2）；2.0.0 写下的记录老版本照读（不认识就忽略）。**不写迁移脚本、不改目录名、不改文件名规则**（id 规则不变，`lib/memory/conflicts.js:229-231`）。⚠️ 唯一要小心的是「两份正文」在矛盾记录里的语义（`incoming` = 新说法），写进决定与面板文案，不靠字段名自解释。

### 10.4 npm 大版本升级提示（草稿）

> **2.0.0 是行为变更版。** 升级后：① 被标 `invalid_at` 的记忆不再注入正文；② 有未裁决矛盾的记忆不进正文，直到你在「记忆管理 → 冲突」里裁决；③ 没标注的旧记忆行为不变，不需要迁移。回退到 1.9.x 不会坏数据，但「失效」标记会失效、冲突页签会消失。详细口径见 README「写入安全」「检索与注入」两节与 `CHANGELOG.md` 的 2.0.0 一节。

### 11.1 风险清单

| 风险 | 表现 | 现在的防线 |
|---|---|---|
| **模型误标**（把「有更新」当「旧说法作废」） | 本来有效的记忆被藏起来 | 只标不删、可撤销、逐条可见、状态卡说条数、整理声明留痕 |
| **模型漏标** | 旧说法继续注入（现状） | 是「未验证」的准确率问题，不承诺；评测只测消费侧 |
| **冲突记录增长** | 每趟整理给同一对新增一条 | 去重（`lib/autodream/tools.js:653-670`）+ 面板批量处理（后续版本） |
| **写 frontmatter 写坏文件** | 乱序、重复键、CRLF 变 LF | 只加键、先剥后插（`lib/memory/scan.js:93-107`）、原子写、套件逐字节比对 |
| **抑制造成「记忆消失」观感** | 用户不知道为什么没注入 | 状态卡 + 徽标 + 工具仍可读；这是 D27 教训的正面回应（`docs/decisions.md:632`） |

| **降级静默失效** | 回退后标记不生效 | §10.2 写清、升级提示写明 |

### 11.2 需要拍板的 8 个问题

> **2026-10-27 已拍板：8 条全部选推荐项（A），另有三处设计稿没写全的落地口径（`invalidatedFile` 字段、指纹排除空 otherFile、`report_contradiction` 内部工具）与「不做 alpha 切片、直接发 2.0.0」的决定，结论见 `docs/decisions.md` 的 D29。下面 A/B 与代价保留原样作为决策依据。**

每条两个选项与代价。**首选写在前面，但决定权不在设计稿。**

**Q1 抑制范围：只对矛盾型，还是所有未裁决冲突？**
- A（推荐）只对 `contradiction`：写失败型不抑制。代价：`stale_version` 记录永远不会让记忆退出注入，用户可能长期不处理。
- B 所有 open 记录都抑制：口径统一。代价：一次没写进去的失败会让盘上那份**有效的**记忆被藏起来，直到人工处理 —— D27 担心的正是这个。

**Q2 失效标记写在哪？**
- A（推荐）记忆 frontmatter：自包含、可 git diff、状态根丢了也在。代价：裁决要写用户文件，必须走版本守卫，写失败要处理。
- B 状态目录旁路索引：不碰用户文件。代价：状态根一丢标记全没；同一事实两个出处；记忆目录不再自包含。

**Q3 失效记忆还能被 `search_memory` / `read_memory` 读到吗？**
- A（推荐）能读到，结果追加 `invalidAt`：问历史时旧口径是证据。代价：模型可能拿旧口径当现状，需要提示语。
- B 默认过滤、要显式参数才给：更安全。代价：改工具参数面（契约 3.2 的封闭 schema），模型失去查历史的入口。

**Q4 面板落点：新页签，还是塞进现有位置？**
- A（推荐）第 6 个页签「冲突」+ 头部徽标：动作多、需逐条看。代价：改页签快照断言、导航多一格。
- B 工具抽屉 / 文件列表内嵌：不动导航（D25 抽屉先例）。代价：发现性差，多步流程塞进抽屉难用；徽标仍要加。

**Q5 矛盾怎么产生？**
- A（推荐）自动做梦的整理声明里列出、引擎落记录：不加公开工具面，不碰契约 3.1 / 3.2。代价：只在整理时检测，有延迟。
- B 新增模型工具 `mark_conflict`：随时可标、实时。代价：永久多一个公开工具与 schema，等于给自动裁决留暗路，且要改契约与文档。

**Q6 状态卡要不要加冲突那一句？**
- A（推荐）加：抑制必须可见（D27 的直接教训）。代价：卡池只有 512 字节（`lib/memory/status.js:15`），会挤占别的提示；多一条断言。
- B 不加，只靠面板徽标：卡保持干净。代价：用户不看面板时，一条记忆悄悄不被注入 —— 正是要防的事故。

**Q7 评测语料怎么处理？**
- A（推荐）在现有 `l*` / `m*` 语料上加标记并重立基线：同一批题能前后对照。代价：旧基线作废，指标要重讲口径（D12 / D19 的摩擦）。
- B 新建一套「带标记」语料与题集，旧基线不动：新旧互不干扰。代价：两套语料长期并行维护；跨版本比较只能靠 `--diff` 考古、不能当门禁。

**Q8 要不要加运行时总开关（例 `SAGE_MEM_VALIDITY=0` 关闭失效过滤与矛盾抑制）？**
- A（推荐）加：出问题用户能自己关掉，不用降级整包；也让真机验收能 A/B。代价：多一个环境变量进契约 §5、多一组断言、多一条「关掉后行为如何」的文档。
- B 不加，回退靠降级 1.9.x：契约面更小。代价：降级要重装包、失去本版其它修复；临场处置更慢。
